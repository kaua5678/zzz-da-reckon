# 下一轮委托：意图与验收闸门

> 给本地首席协调 agent。本文规定“为什么做、何时值得做、什么不能做”，不是现场操作手册。
> 配套文件：`round2-field-sheet.md`，由执行者现场核验填写。
> 本文取代上一版交接中被当作通用规则的环境、工具、路由和端口要求；旧材料仅供追溯，不直接继承其操作条款。

## 1. 分工与知识边界

**云端协作方负责把用户的担心转成明确闸门；本地首席负责采集事实、选择任务、验证接口、拆单和集成。**

我只掌握用户转述的上一轮反馈，没有本地当前状态、工具 schema、执行回执或完整交付证据的可见性。我不知道最新修订、文件归属、可用路由、运行入口、资源端点，以及上一轮各项结论的完整覆盖范围。因此不预填这些内容，也不再列举“可能可用”的接口名。

你不需要等待云端替你确定具体缺陷清单。按现场证据选择下一项真实收益，在以下意图与权限边界内裁剪任务；现行项目规范已有的操作要求直接引用，不要重新抄成另一套手册。

## 2. 长期有效的六条意图

1. **防假绿。** 先证明指定错误能被指定检验以正确原因识别，再谈修复。环境故障、夹具错误或无关断言变红，不算目标反例；找到元素、字段存在、数字不变，也不自动等于行为正确。
2. **防过度重构。** 不因相似命名、多个写入点或一个案例就建立通用框架。证明到一个实例就点修；需要泛化时，另证共同原因、适用范围和维护收益。
3. **防凑绿。** 不用删测、弱化判据、掩盖跳过或无归因调整基线换取成功。合法口径修正可以导致数字变化，但必须先解释变化，再处理验收依据。
4. **允许不立项。** 审计证伪是有效成果，不要求每个工人都交代码。负结论必须有范围，不能扩大成永久豁免；重开需要新的可观察证据，不是换个名称重做。
5. **不以清单代替语义。** 文档清告警、状态标记或静态引用只是线索。能证明到哪里就写到哪里；不能把尚未确认的机制、行为或来源说成已验收。
6. **防知识膨胀与转述失真。** 保存可追溯证据和简短结论，不制造编年账本或重复真源。首席必须独立判断，不能把工人的“通过了”直接转述为自己的验收结论。

## 3. 每条任务强制附两行证伪闸门

在派工前写明，不在看到结果后改写前提：

> **前提假设：** 哪个具体对象、行为或承诺存在什么尚未证实的问题，为什么值得本轮投入。
>
> **假设为假时的可观察失败：** 什么观察会否定这项立项理由；出现时停止哪一步、保留什么结论。

这两行不是“前提：有 bug；证伪：没 bug”，也不是修复验收条件的换个说法。必须落到可识别的对象、输入、出口和证据。修复完成的成功判据另列。

例如：若假设是“某种错误无法被现有检验看见”，证伪条件应是“受控反例已被现有检验稳定地按目标原因识别，且合法对照不被误报”。此时应停止补造同功能检验，而不是修改反例或观察口径来制造缺口。

无论是实现、调查还是文档修正，只要独立派成任务，都必须有这两行。纯粹填表、重复复核已有结案，不应包装成新的开发产出。

## 4. 下一轮任务方向——供现场选择，不是已确认缺陷

本轮目标是推进**有证据支持的增量**，不是扩大调度体系。以下方向可选、可裁掉，也可被现场更有价值的真实问题替代；每项仍须重新写成具体闸门。

### 候选一：一个尚未收口的实际行为

- **前提假设：** 现场能定位一个仍活跃、业务含义已明确的问题或验收盲点，并能构造隔离的反例或可区分的错误形态。
- **假设为假时的可观察失败：** 同等输入与约定出口下，现有实现和正反控已经覆盖该问题；或差异仅来自环境、未裁定口径、非活跃消费者。此候选不进入修复，不靠改换观察口径凑出缺陷。

先交最小证据，再决定是否授权实施。限定一个可闭环的对象，不自动扩大为全库普查或架构重写。

### 候选二：一条确实会误导决策的陈述

- **前提假设：** 当前一条活跃说明、状态或承诺与可核对的实现存在具体偏差，并影响用户或后继执行者的判断。
- **假设为假时的可观察失败：** 原记录已经清楚限定范围、不确定性和真源位置，按其指针即可复核；新增文字只会重复事实或记录历史。此候选不立项，不为“整理资料”另建账本。

成立时只修正唯一真源或必要指针。没有语义证据，不得用补状态行、消除告警或复制大段实现来冒充完成。

**上述假设不能原样抄进工单就开工。** 首席须填入现场对象、可观察条件、收益、范围和停止条件。若没有值得投入的候选，可以给出有边界的不立项结论。

## 5. 权限与升级条件

- 首席负责现场选题、技术拆分、精确白名单、证据审查和集成判断；工人只执行授权任务，发现范围外事项先报告。
- 白名单由现场确定。先复现/取证与后实施是两个授权阶段；前者成立不代表后者已获无限修改权。
- 业务含义不明确、来源无法确认、需要扩大权限或新增开销、涉及未授权发布或不可逆处置时，升级给用户。
- 范围内的技术选择不必反复询问用户；不存在的工具、未核验的权限、未知执行结果不能靠猜测补齐。

## 6. 什么算本轮交付

交付可以是：有证据且通过约定验证的改进、范围明确的有效否决，或精确说明缺口的阻塞结论。

首席总结必须区分：**做了什么、证明了什么、没有证明什么、哪些任务明确停止、什么新证据才值得重开。** 不以代码量、文档长度、告警数量或模型名称作为成绩。
