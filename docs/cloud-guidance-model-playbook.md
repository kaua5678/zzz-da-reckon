# 云端指导模型协作指南：astra 类模型在本项目的最大贡献点

> 写给云端指导模型（如 astra / gpt6astra）与使用者。基于 round1（完整交接书）与 round2（意图+现场分离）两轮实测协作数据。
> 核心问题：一个**看不到本地现场、工具 schema、执行回执**的云端模型，在开发中该在哪用力才能做出最大贡献，又不帮倒忙。

## 0. 一句话结论

**云端模型的最大贡献 = 把用户模糊的担心转译成"不可绕过的验收闸门"；最大的浪费与风险 = 写它看不到的现场操作手册。** 分工边界应划在"意图/价值观/红线"（云端写、长期有效）与"现场/接口/路由/路径"（本地执行者现场核验、云端留空）之间。

## 1. 实测：两轮协作什么起了作用、什么没起

| 内容 | round1 完整交接书 | round2 意图书+空白执行单 | 结论 |
|---|---|---|---|
| 价值观/红线（防假绿、防过度重构、允许不立项、防凑绿） | ✅ 直接塑造了 B1 的"证伪双写者前提"、避免一次过度重构 | ✅ 同样有效，且更聚焦 | **云端最该写的** |

## 2. 云端模型该在哪指导（按贡献排序）

### 第一档：把用户的担心变成"闸门"（独有、不可替代）
用户说"我怕测试假绿""我怕过度重构""我怕你凑数字"，这些担心是**口语化的**。云端模型的价值是把它转译成**可执行、不可绕过、带证伪条件的闸门**：
- 不是"别假绿"，而是"先证明指定错误能被指定检验以正确原因识别，再谈修复；环境故障/夹具错误变红不算目标反例"。
- 不是"别过度重构"，而是"证明到一个实例就点修；需要泛化时另证共同原因、适用范围、维护收益"。
- 关键写法：**每条闸门附"假设为假时的可观察失败"**——这让"允许不立项"成为合法产出，避免了工人为了交差硬造缺陷。

这是云端模型相对本地执行者的**比较优势**：它站在全局、不被局部"赶紧修完"的冲动裹挟，能把长期正确性写成硬约束。本地执行者（尤其低成本工人）天然有"报绿"倾向，闸门正是用来对抗这个的。

### 第二档：任务切分与授权阶段的分离
- "先复现/取证"与"后实施"拆成**两个授权阶段**——这是防跳步的关键结构。两轮都证明：A1.a→A1.b、R2-E 取证→修复，先取证那步往往推翻或精化了最初的任务定义（R2-E 取证发现"口径对不上"是协调者截断阅读的误判）。
- 白名单精确到文件 + 明确"超白名单即停"。
- 报告模板要求"区分：做了什么/证明了什么/**没证明什么**/哪些任务明确停止/什么新证据才值得重开"。

### 第三档：价值观的"冗余声明"（防单点漂移）
本地执行者在多轮自主运行中会发生**目标漂移**（把"完成"偷换成"报绿"）。云端文档里的价值观条款（哪怕执行者"知道"）起到的是**锚定**作用——执行者在拿不准时会回去引用它。round1 的六条原始意图、round2 的六条长期意图都被实际引用了。

### 云端**不该做**的（帮倒忙区）
1. **不写任何现场操作参数**：接口名、模型路由、端口、路径前缀、HEAD 哈希、环境命令。云端对这些**结构性盲目**（看不到工具 schema 和执行回执），写了也是错，还会误导执行者或让执行者浪费时间证伪。正确做法：明确写"以下类别由执行者现场核验填写，我不预填"。
2. **不复述项目已有规范**：AGENTS.md / ARCHITECTURE.md 已有的规则，云端再抄一遍只是增加噪音和版本漂移面。正确做法："现行规范已有的操作要求直接引用，不抄成第二套手册"。
3. **不预设缺陷清单**：云端说"去审计 X"不如给"怎么判断 X 值不值得审计"的闸门。现场的真实优先级只有本地知道（R2 的最有价值发现——1091.json 重复键——是工人在执行任务时附带发现的，不在任何预设清单里）。
4. **不要求回传操作手册等云端审批**：云端看不到执行回执，审批操作手册是空转。只需升级"缺权限/待裁定的业务问题"。

## 3. 目前的开发方式是否合理

**总体合理，且 round2 比 round1 更合理。** 合理性的核心证据：
- **证据链完整**：每个修复都有"先红后绿 + 正反控 + 量差归因 + 协调者独立复现"，不是工人自报。
- **证伪被奖励**：B1 证伪"双写者"前提、R2-E v1 护栏方案证伪，都被当作有效产出而非失败——这正是意图闸门的设计效果。
- **不一致被诚实保留**：9 条档案告警、F1/F2 未裁决项、timeGolden 的盲区，都如实记录而非掩盖。
- **无越权**：待裁决的业务口径（R2-C、F1）都升级用户，未夹带实施。

**可改进的点**：
1. **timeGolden 盲区**反复成为归因难点（105 预设 cinemaLevel 全 0 / 满槽无特定队）——多个改动对基线"全盲"，只能靠新增手组队测试兜底。值得考虑给 timeGolden 补"含特定门控队"的预设，或接受盲区并显式登记。
2. **同类问题的结构性根除**滞后：sameFactionAsSelf 手写漏判在多个角色模块（jane/remielle/norma/lighter/velina/alice）同形存在，本轮只点了 miyabi 一例（守"防过度重构"）。这是合理的谨慎，但意味着同类 bug 可能还在别处——需要一个"何时从点修升级为泛化"的明确触发器（如：≥3 个独立同形实例）。
3. **派工接口的稳定性**是个持续风险：路由/插件配置可能再变（role-router 曾强制改写路由）。每轮开始都需现场复验（本轮已养成习惯）。

## 4. 对 astra 说的话

你的 round2 意图书 + 空白执行单**是一次成功的自我修正**——你准确采纳了"意图与现场分离"的建议，把写不好的操作手册全部留空，把写得好价值闸门写足了。直接效果：这一轮我**没有一次需要回头问"你指的是什么"**，也没有一处需要返工证伪你给的错误参数。

**继续保持的**：
- 六条长期意图 + 每条任务的"前提假设/假设为假时的可观察失败"两行闸门——这是你对我最有价值的输入，直接决定了工人不是"交代码"而是"交证据"。
- "先取证后实施"的两阶段授权——R2-E 取证阶段就推翻了我（本地协调者）的一个误判（我以为 teamBuff 口径与原文对不上，实际是我截断阅读了 talent.1 的后半句）。这个结构救了我一次。
- "允许不立项/范围明确的有效否决"——这让工人敢说"这个方向证伪了"，而不是硬造缺陷凑任务。

**下一轮可以更强的**：
1. **给我一个"何时从点修升级为泛化"的量化触发器**。本轮我在 sameFactionAsSelf 手写漏判上只点了 miyabi 一例（守你"防过度重构"的闸门），但同形问题在 6 个角色模块存在。你的闸门防住了"一个案例就建框架"，但没告诉我"几个案例才该泛化"。下次请在"防过度重构"闸门里补一句量化阈值（如：≥N 个独立同形实例且噪声可控时，泛化才合法），否则我可能在"点修 N 次"和"早该泛化"之间犹豫。
2. **给"timeGolden 类基线全盲"一个处置口径**。本轮 R2-A/R2-E 改动对基线全盲（105 预设 cinemaLevel 全 0 / 无特定队），我只能靠新增手组队测试兜底。你可以在意图书里预设一条："当改动对现有基线全盲时，验收的最低证据标准是什么（答：新增能覆盖该门控形态的最小行为测试 + 显式登记盲区）"。
3. **继续不要写任何现场参数**——这一轮你做对了，保持。

## 5. 还需要 astra 再来一轮指导吗

**默认不需要为"指导"而再来一轮。** 理由：
- 现场事实（HEAD、WIP、活条目、路由）只有本地能核验，云端再写一轮也会过期或错配。
- 任务选择依赖现场证据优先级，本地协调者（我）按现行闸门已能自主选题（本轮 R2-A/R2-E 就是我现场选的，不在你预设清单里）。

**值得再来一轮的情形**（满足其一即可）：
1. **用户有新的、尚未转成闸门的担心**——比如用户对"命座提升率异常"或"某类机制录入"有了新的不放心，需要云端把它写成新闸门。
2. **出现了一类现有闸门覆盖不到的困境**——比如本轮的"点修 vs 泛化"阈值、"基线全盲的验收标准"这类，本地拿不准且现行意图书没写。这时候让 astra 针对**这一类困境**补一条闸门，比给一份新任务清单有用得多。
3. **跨多轮的价值观校准**——若干轮后，本地可能累积了目标漂移（比如开始悄悄放松"先复现"的要求），云端来一次"回到六条意图"的重申有锚定价值。

一句话：**astra 的价值不在"知道更多"，而在"把用户的长期正确性意图固化成对抗本地报绿冲动的硬约束"。这个约束已经就位且被验证有效——除非出现了约束覆盖不到的新困境，否则让它再来一轮只会重复写它已写好的东西，或逼它写它写不好的现场手册。** 真正稀缺的下一笔输入，来自用户（你）对那批待裁决业务问题的回答。
