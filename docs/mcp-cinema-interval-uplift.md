# 命座 × 难度曲线：台阶跳变、区间提升口径，与一条真缺陷

**立项**：用户 2026-11-04。本文是**专项口径 + 实测证据**，不含编年叙事（那些在 git log 与 `.claude/` 账本）。

用户原话（逐字）：

> 命座掉伤害是因为台阶跳变，这个我需要做一个专项。一个命座水平在难度曲线上覆盖一段 y，
> 加命座会把 y 区间上移，但是区间有重合，特定的某个 y1 可以找到更低的 y2。这就是副作用的由来。
> 我想玩家看命座肯定想看这种客观的区间提升，而不是取两点发现命座说伤害提升了但计算器算出来是负的。

要回答三件事：① 「取两点」为什么会产生负值；② 「区间提升」到底是什么量、怎么算；③ 负值里有多少是
台阶跳变（可解释、不该改数），有多少是**引擎缺陷**（必须修）。

## 1. 结论先行

| # | 结论 | 证据 |
|---|---|---|
| ① | **两级曲线的点根本不是同一批难度**（点数/域都不同）⇒ 「同名档逐点比」连「同一点」都对不上 | §2.1 |
| ② | 即使把两级曲线拉到**同一固定网格**，「同难度比伤害」在中低难度端**全部为正**（+0.88% ~ +7.52%），负值只出现在**高难度端** | §2.2 |
| ③ | **命座本身是正提升（+1.1%~+2.1%）**：那 −12% 全部是 C3 多拿的一份白送 | §3.0 |
| ④ | 白送 = `[表]` 直读在**模块沉默**时按满倍率免费接管（不花闪能、不占时间） | §3.1 |
| ⑤ | **源头**：同一轮里「轴内几窗」有三个数——计划窗 0.137（nec 余量）/ 执行集合 5 / 伤害覆盖率 5。模块读最小的那个⇒沉默；系统用另外两个出伤。`allocateAxisWindows` 的窗口数入参**只统一了一半** | §3.2 / §3.3 |
| ⑥ | 三条修法臂实测：A 去 `backed` 门 = 重复计伤；B 模块读执行集合 = **+1.95%（正）**、白送退场并付代价；C `wins` 取整 = 逐位相同（非载体） | §3.4 |
| ⑦ | **「区间提升」口径成立**：一个命座水平 = 一条 `(难度 x, 伤害 y)` 前沿；比的是两条前沿（同难度比伤害 / 同伤害比难度），不是各自的最优点 | §4 |
| ⑦ | 修法需要一条**口径裁决**：`[表]` 直读「模块沉默就白送」这条是否保留。实测里 A 臂会重复计伤，**B 臂是唯一自洽解**（两套账合一）⇒ 本文给出证据与判据，**未擅自改引擎** | §5 |

## 2. 实测

夹具：`yixuan-jufufu-lucia` / `yixuan-roxy-lucia` / `yixuan-trigger-lucia`（主 C 都是仪玄 1371，槽 0），
探针 `.zc/perf/cinema*.perf.ts`，跑法 `npx vitest run --config .zc/perf/vitest.perf.config.ts <探针>`。

### 2.1 两级曲线不是同一批点

`climbDifficultyLadder` 逐队收敛出的落点（`cinemaNegativeWhere.perf.ts`）：

| 队 | C3 落点 | C4 落点 |
|---|---|---|
| `yixuan-jufufu-lucia` | x=0 / 3.5 / 6.9 / 29.6 | x=0 / 2.9 / 6.9 / 29.6 / 38.1 |

同一支队的相邻两级**点数不同、x 也不同**。于是「同名档逐点比」（页面现行的 `cinemaUplift` 口径：
只变命座、其余全同）在这条曲线上**根本没有可比对**——它比的是「C3 的第 3 点」与「C4 的第 3 点」，
而这两个点落在不同难度上。这就是用户说的「取两点」的第一层副作用。

### 2.2 固定网格上重采样后，负值只剩高难度端

在**同一批 `(parry, dodge)` 网格**上采两条前沿（`cinemaFrontier.perf.ts`，取累积最大 y 的上包络），
再按「同难度比伤害」（C_hi 在 `x' ≤ x` 内的最高 y）逐点比：

| 队（C3→C4） | 同难度比伤害逐点 | 最差 | 最好 |
|---|---|---|---|
| `yixuan-jufufu-lucia` | x=0 **+1.85%** / x=3.5 −2.98% / x=6.9 **+2.51%** / x=29.6 **−11.79%** | −11.79% | +2.51% |
| `yixuan-roxy-lucia` | +2.89 / +2.88 / +2.83 / +0.88 / +2.75 / +2.82 / **+7.52** / −2.07 / −2.88 | −2.88% | +7.52% |
| `yixuan-trigger-lucia` | +2.72 / +2.69 / +3.50 / +2.60 / +2.58 / +2.25 / −1.88 / **−9.80%** | −9.80% | +3.50% |

⇒ **负值不是「区间重合」的必然产物**：低到中等难度上 C4 稳定更好；负值集中在**难度域的最高端**
（x=24~30 一带，正是 C3 拿到幻影行的位置）。所以「区间口径能把负提升洗掉」这个假设**被证伪**——
洗不掉的 3 个点是一条真缺陷。区间口径仍然要上（§4），但它不是用来掩盖负值的。

### 2.3 高难度端到底发生了什么

同一 (parry=20, C3/C4) 的伤害池行（`cinemaBacked.perf.ts`）：

| 命座 | 凝云术 1371022 | 墨烬影消 1371026 | 来源 |
|---|---|---|---|
| C3 | **×15** = 3.46M | **×15** = 1.21M | `轴内·技能表直读` |
| C4 | ×1 = 0.53M | ×1 = 0.18M | 模块行 `1371022` / `1371026` |

其余执行数**完全一致**（`ex=15`、`ult`、前台时间、轴窗 5），伤害却差 4.31M —— 差额几乎全在这两行。

同时读闪能账（`cinemaAlloc.perf.ts`）：

| parry | C3 墨痕化形 #1 / 凝云 | C4 墨痕化形 #1 / 凝云 |
|---|---|---|
| 16 | 14 / **15** | 12 / **2** |
| 20 | 15 / **15** | 14 / **1** |

⇒ C3 的 15 次凝云**不花闪能也不占时间**（直读行「不占时间预算、窗内不产失衡值」是引擎既定口径）；
C4 的 1 次是要付 60 闪能的真循环。两条曲线因此不可比。

## 3. 根因：**「模块沉默」本身有价**

### 3.0 先算清楚：**命座并没有掉伤害，是 C3 被抬高了**

把伤害池里 `轴内·技能表直读` 的行**原价扣掉**（只做算术，不重跑资源链），三支队 C3→C4：

| 队 | C3 原值 | C3 虚高占比 | C3 洁净值 | C4 原值 | 原值 Δ | **洁净 Δ** |
|---|---|---|---|---|---|---|
| `yixuan-jufufu-lucia` | 36.600M | **4.671M / 12.76%** | 31.929M | 32.286M | −11.79% | **+1.12%** |
| `yixuan-trigger-lucia` | 29.442M | **3.429M / 11.65%** | 26.013M | 26.556M | −9.80% | **+2.09%** |
| `yixuan-roxy-lucia` | 26.032M | 0（无表行） | 26.032M | 26.531M | +1.91% | **+1.91%** |

⇒ **命座是正提升（+1.1% ~ +2.1%），一切正常**。那 −12% 全部来自「C3 有一份 C4 没有的白送」。
这不是「命座把伤害削了」，而是**测量把 C3 抬高了 12.76%**。

⚠ 洁净 Δ 是**算术剥离**（把白送行减掉），不是重跑资源链的下限——真实重跑要连白送腾出来的闪能一起收回去，
数字会更高（§3.4 的「同源臂」：+1.95%）。

### 3.1 白送是什么：`[表]` 直读在模块沉默时**按满倍率免费接管**

`resourceCalc/axisTableDirect.ts#axisTableDirectMove` 判据 ② 按 moveId 的**存在性**判
（`backed = Set(executions.moveId)`，不看条数）。于是：

| | 模块有没有产 1371022 的行 | `[表]` 直读 | 实际结算 |
|---|---|---|---|
| **C3** | **0 行**（沉默） | **成立** | 凝云×15 = **3.46M**，**不收闪能、不占时间**、窗内不产失衡值 |
| **C4** | 1 行（静心强制 cloudOut ≥ 1） | **关闭** | 凝云×1 = 0.53M（要付 60 闪能的真循环） |

同一招、同一份轴计划（执行集合都是 `1371022×15`），一份收 0 代价、一份收全额代价。
**「不产行」在这个体系里是收益**——这就是负提升的全部来源。

### 3.2 模块为什么沉默：计划窗 0.137 是**容量余量**，不是物理窗数

`yixuan.ts#applyYixuanTeamConfig`（converge）用 `forEachSlotAxisAction` 数轴内块：
`act.count × axis.windows[ai]`。而 `axis.windows` 在同一次 converge 里是**计划值**，
它被 `solveTeam` 的「非失衡时间充足性约束」按住：

```
nonStunTime = effTime − next × W  <  Σ necessaryTime
  ⇒ next = (effTime − Σnec) / W          // solveTeam.ts 的 nec 约束
```

实测（`cinemaNecPressure.perf.ts`，`yixuan-jufufu-lucia` / parry=20）：

| 命座 | 池窗（`stunPool.stunCount`） | W | Σnec | (eff−Σnec)/W | 计划窗 |
|---|---|---|---|---|---|
| C3 | **5.000** | 19.0 | 177.40 | **0.137** | 0.1369 |
| C4 | **5.000** | 19.0 | 176.21 | **0.199** | 0.1994 |

- `1 块 × 0.137 窗 = 0.137` → `positiveWholeCounts` 向下取整 → **丢弃** → `cfg.yixuanAxisEx` 里 1371022 = 0；
- 而**同一轮**的执行集合用的是 `threads.prevPoolStunCount ?? countStun` = **5 窗** → `actionCountsBySlot = 1371022×15`；
- 伤害侧也按池结算：`stunCoverage = 5 × 19 / 180 = 0.5278`（实测读数逐位吻合）。

⇒ **同一轮里，「轴内几窗」有三个数**：计划 0.137 / 执行集合 5 / 伤害覆盖率 5。
模块读到最小的那个，于是沉默；系统用另外两个数出伤。

### 3.3 源头：这两个数为什么能同时存在

`convergence.ts` 同一轮里 `allocateAxisWindows` 被调用多次，**窗口数入参不统一**：

| 用途 | 窗口数入参 | 位置 |
|---|---|---|
| 决算截断 / `axisInSeconds` / 派发给模块的 `axis.windows` | `stunCount`（**计划**，0.137） | `convergence.ts` 的 `winAlloc` / `axisInSeconds` / `axis.windows` |
| 轴栈执行集合（`actionCountsBySlot` / `axisUltimateTotal` / 合轴节省） | `threads.prevPoolStunCount ?? countStun`（**池**，5） | `calcStunAxisStack` 的 `stunCount` |

后者有一行**写明了理由**：「轴块是『块 × 窗』的整数执行……与雨果决算行及伤害侧栈同源」。
前者（派发给模块的 `axis.windows`）没有跟着改——**同源纪律只落实了一半**。

这就是「两套账」的最底层形态：不是两个模块各算各的，而是**编排层给同一个量喂了两个输入**。
只要计划窗 < 1（实测 `yixuan-jufufu` 0.137、`yixuan-trigger` 0.353），模块必然沉默；
而池窗 ≥ 4，系统必然按 4~5 窗出伤。**沉默是结构性的，不是偶然**。

### 3.4 三条修法臂（都实测过）

| 臂 | 做法 | parry=20 C3 / C4 | Δ | 性质 |
|---|---|---|---|---|
| 现状 | — | 36.60 / 32.29 | **−11.79%** | 白送 12.76%，C4 没有 |
| A 去 `backed` 门 | 让表行与模块行共存 | 43.22 / 43.58 | +0.8% | ❌ **重复计伤**（同一招算两遍，比现状还高） |
| B 模块读执行集合 | `yixuanAxisEx` 改读 `axis.actionCountsBySlot`（与般岳同源） | 34.78 / 35.46 | **+1.95%** | ✅ 两套账合一，白送退场并**付代价** |
| C `wins` 取整 | 对 `axis.windows` 做 `ceil`/`round` | 与现状**逐位相同** | 0 | ❌ 不是载体（`act.count × wins` 的小数是被 `positiveWholeCounts` 按记录丢的） |

B 臂的绝对变化：**C3 36.60 → 34.78（−5.0%）**。这不是退步——那是把白送的 15 次凝云换成
**要付 900 闪能的真循环**（实测同臂 C3 墨痕化形 #1 从 15 次掉到 3 次，闪能全给了凝云）。
$$`[表]` 该不该免费这一问，B 臂给的答案是「不该」**。

## 4. 「区间提升」口径（用户要的客观量）

### 4.1 定义

一个命座水平在难度曲线上不是**一个点**，是**一条前沿**：

```
前沿(C_n) = { (x, y) : x = 操作难度, y = 该难度下的最高伤害 }
```

实测采样后取 **累积最大 y 的上包络**（只有包络才是「这条命座水平的上限」，散点是网格噪声）。
比较两条前沿有两种等价读法，**都必须给**：

| 读法 | 定义 | 回答的问题 | 符号 |
|---|---|---|---|
| **同难度比伤害** | 对 C_lo 的每个 x，取 C_hi 在 `x' ≤ x` 内的最高 y | 「同样的操作难度，加了命座能多打多少」 | Δy ≥ 0 才叫提升 |
| **同伤害比难度** | 对 C_lo 的每个 y，取 C_hi 达到 y 所需的最小 x | 「打出同样的伤害，加命座能省多少操作」 | Δx ≥ 0 才叫提升 |

### 4.2 三条判据（写进实现时按这个判）

1. **不能拿各自的最优点比**：`max y(C_hi)` 对 `max y(C_lo)` 是「两条曲线的端点比端点」，
   端点落在不同 x 上 ⇒ 正是用户说的「特定的某个 y1 可以找到更低的 y2」。
2. **必须披露 x 域重叠**：两级的 x 域不同（§2.1），域外只能单向报（「C_hi 在这个难度上够不到」= 未定义，
   不是 0、也不是负）。
3. **负值必须能被追问到行级**：区间口径仍可能给出负值（§2.2 的 −11.79%），此时页面/专项必须能下钻到
   「哪一行少了几个」，否则读者只能猜是台阶还是 bug。

### 4.3 与现有实现的关系

- `composables/cinemaUplift.ts#analyzeCinemaUplift` = **单场景逐级**（锁失衡次数、只变命座）——
  它是「同一点上的两点比」，**不是区间比**；本文不主张替换它（它是「死数据自检」的检测器，
  AGENTS 规则 5 依赖它），而是**并列**一条区间口径。
- `composables/cinemaUpliftGrid.ts` 已经承认「命座提升率不是角色的内禀属性」（多锁值 / 多 Boss / 多 buff），
  区间口径是同一个思想的第三个维度：**多难度**。
- 数据来源必须是**阶梯**（`difficultyLadder#climbDifficultyLadder`）或**固定网格**；
  只取首尾两点会退回到 §2.1 的缺陷。

## 5. 修法（**B 臂是唯一自洽解**；落地需一条口径裁决）

### 5.1 推荐：模块计数改读**执行集合**（B 臂）

`yixuan.ts#applyYixuanTeamConfig` 的轴内块计数从 `forEachSlotAxisAction`（`axis.windows` = 计划小数）
改读 `axis.actionCountsBySlot[slot]` —— **与般岳同源**（`banyue.ts` 的 `cfg.banyueAxisEx = axis.actionCountsBySlot[slot] ?? {}`）。

实测（parry=20，`cinemaPinWins.perf.ts` / `cinemaExecutedCounterfactual.perf.ts`）：

| 队 | C3 | C4 | Δ |
|---|---|---|---|
| `yixuan-jufufu-lucia` parry=20 | 36.60 → **33.07** | 32.29 → **33.61** | −11.79% → **+1.63%** |
| `yixuan-jufufu-lucia` parry=16 | 35.56 → **31.94** | 31.64 → **32.49** | −11.02% → **+1.72%** |
| `yixuan-trigger-lucia` parry=20 | 29.44 → **26.88** | 26.56 → **27.31** | −9.80% → **+1.60%** |
| `yixuan-trigger-lucia` parry=16 | 25.43 → **25.67** | 25.79 → **26.10** | +1.42% → **+1.68%** |

**会动的数字**：仪玄在所有轴队在**高交互档**下的伤害（C3 侧最大 −5.0%，因为白送退场）。
⇒ 按规则 10 跑 `timeGolden` / `timeFillRatchet` 并逐队归因。

**代价 / 风险**：
- 仪玄从此与「计划口径」的另几家（春正/朱鸢/希格/伊德海莉/比利）不同源——但那几家的白送风险相同，
  这是**逐家暴露**而不是破坏分工；`stunWindows.ts` 头注释本就写明「读哪一个是各模块的产品口径」。
- 需要一条判据防止回退（见 5.3）。

### 5.2 同时要堵的：`[表]` 直读的**存在性门**

即使 B 臂让模块产行，`backed` 门仍会把「模块只表达了一部分」的招式整体交给模块。
B 臂落地后仪玄不再沉默，这条门对它是安全的；但对**任何未来在低计划窗下沉默的模块**，
白送会立刻复现（同一形态，不同角色）。⇒ 建议把判据改成**按条数认领**：

> 模块对某 moveId 有执行行时，`[表]` 只补「轴计划数 − 模块已表达数」；为 0 时不补。

这需要模块上报「轴内表达了多少」——B 臂落地后 `actionCountsBySlot` 就是那个数，
所以 5.1 是 5.2 的前提。

### 5.3 判据（落地后必须绿）

1. **不得再出现「模块 0 行 + 表行 × N」**：某 moveId 的池行里，若 `[表]` 行存在，
   则该槽的执行集合在**同一轮**里该 moveId 的次数必须为 0（现状 C3 违反：表 15 次 vs 执行 15 次）。
2. **同一轮「轴内几窗」只有一个数**：`axis.windows` 派发值、`actionCountsBySlot` 的窗口基数、
   伤害侧 `stunCoverage` 三者必须可互相推导（现状：0.137 / 5 / 5）。
3. **反空洞**：上述判据在「计划窗 ≥ 1」的队上必须同时成立（否则是恒真）。

裁决点只有一个：**`[表]` 直读在模块沉默时该不该白送？**
实测答案倾向「不该」——它让「不实现」比「实现」更值钱（C3 比 C4 高 12.76%，
代价是同一招不收闪能、不占时间）。

## 5.4 已落地（2026-11-04 第二轮，用户裁决「我肯定选真实计算」）

**源头修复（不是模块补丁）**：`convergence.ts` 引入**单一事实源**
`axisWindowCount = threads.prevPoolStunCount ?? countStun`，让三处同源：

| 用途 | 修复前 | 修复后 |
|---|---|---|
| 派发给模块的 `axis.windows` | `countStun`（计划小数 **0.137**） | `axisWindowCount`（池整数 **5**） |
| 轴栈执行集合 | `prevPoolStunCount ?? countStun` | 同一变量 |
| 伤害侧 `stunCoverage` | 池 | 不变（本来就对） |

## 5.5 剩下的那一格：**外环 2-环交付了坏成员**，不是命座负提升

修复后唯一还是负的：`yixuan-roxy-lucia` parry=16，C0 24.93M vs C4 24.66M（**−1.1%**）。

**⚠ 先纠正一个错误归因**（我第一版写成「C2 符法千重-破抢走平A时间」——被用户当场否定，
「把平A吃掉就是正面提升呀，难道平A已经全被挤没了？」）。实测平A **还剩 4s（两槽各 2.02s）**，
没有挤没；抢时间这个解释与数据不符。真因见下。

### 真因：C4 掉进外层不动点的 2-环，最终交付了环里**较差**的成员

`PROBE_TRACE_OUTER` 逐轮（`cinemaCycleMember.perf.ts`）：

| | C0 | C4 |
|---|---|---|
| 前 5 轮 | `in=1.320→1.256→1.263→1.262→1.262` **稳定收敛** | **完全相同**（`1.320→1.256→1.263→1.262`） |
| 之后 | 收敛结束 | `0.262→0.442→0.233→0.444→0.232→0.444…` **2-环** |
| 交付 | 池 **3** 窗，24.93M | 池 **1** 窗，24.66M |

⇒ C4 的前几轮与 C0 **逐位相同**，是**后面**的迭代把它推进了环，最后由「环退出 ⇒ 最大自洽可行整数」
结算时落到了池=1 的成员上。

**决定性对照**（`cinemaLock3.perf.ts`，把窗口钉死）：

| | 自由 | 钉 3 窗 |
|---|---|---|
| C0 | 24.93M（池 3） | 25.31M |
| **C4** | **24.66M（池 1）** | **31.92M（池 3）** |

⇒ **C4 的真实水平是 31.92M，比 C0 的 25.31M 高 26%**。命座本身是强正提升；
−1.1% 是**收敛器交付了环的坏成员**，不是命座的性质。

### 这为什么是「深层矛盾」的另一面

用户 2026-11-04 口径：命座「只是提供更多选择，不是强制降低」。这里命座新增的动作
（C2 符法千重-破 + C4 墨痕化形）改变了时间账 ⇒ 外层不动点从「稳定收敛」变成「2-环」。
环的两个成员**一个池 3 窗 / 一个池 1 窗**，而环退出规则挑中的是池 1 那个。

⚠ 这条与 §5.1 的源头修复**不同源**：那是「两套窗口数」，这是「不动点收敛失败 + 环选点」。
修法在 `solveTeam` 的 `pickOuterCycleMember` / `kStar` 结算侧，属另一批。

## 6. 否决记录

- ❌ **「C2 符法千重-破抢走平A时间 ⇒ C4 变弱」**（我第一版归因，被用户当场否定）：
  实测平A 还剩 4s（两槽各 2.02s）**没被挤没**；且钉 3 窗后 C4 = 31.92M > C0 25.31M。
  真因是**外环 2-环交付了坏成员**（§5.5），不是时间被抢。
- ❌ **「删 `backed` 门，让 `[表]` 与模块行共存」**：重复计伤。parry=20：C3 43.22M / C4 43.58M，
  比「有白送的现状」还高 ⇒ 同一招被算了两次。
- ❌ **「对 `axis.windows` 取整」**（`ceil` / `round` 两条臂）：与现状**逐位相同**。
  `act.count × wins` 的小数是被 `positiveWholeCounts` 按**整条记录**丢弃的，取整 `wins` 不改变结果。
- ❌ **「用区间口径把负值洗掉」**：固定网格上仍有负值。区间口径是**度量**，不是**修复**。
- ❌ **「把 `[表]` 直读整条删掉」**：它是「模块没建模的招式放进轴也能出伤」的正当通道
  （CC-393 的候选池与结算共用同一判定）。要改的是**模块沉默时的白送价**，不是通道本身。
- ❌ **「保留白送但标注『仅供参考』」**：标注救不了 12.76% 的虚高——它已经进了总伤、进了难度曲线的 y 轴、
  进了命座提升率的分母。
- ❌ **「全库抽样（96 次阶梯爬升）单进程跑」**：20 分钟未出数，已 `job_kill`。下一轮须分片落盘。

## 7. 证伪闸门（下一轮开工前先确认这两条）

1. **前提假设**：C3 的 15 次凝云确实是「表补的、模块没表达」的幻影行。
   **若为假**（例如模块其实在别处表达了这 15 次，只是池行被合并/改名）⇒ 可观察的失败：
   在 `backed` 之外再加一条「按条数认领」的候选①，C3 的总伤**不应变化**；若候选①让 C3 的凝云仍是 15 次
   且总伤不变，说明 C3 本来就没少算，缺陷只在 C4 侧。
2. **前提假设**：修完之后 C3→C4 在**全难度域**上都非负。
   **若为假** ⇒ 可观察的失败：固定网格上仍有任何一个参考点 Δy < 0，且下钻到行级找不到「少了的行」
   ⇒ 说明还有第三层原因（当时的猜测：静心把 60 闪能从凝云搬到墨痕化形，是否本身是净亏）。
