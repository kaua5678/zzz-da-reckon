# 命座 × 难度曲线：台阶跳变、区间提升口径，与一条真缺陷

**立项**：用户 2026-11-04。本文是**专项口径 + 实测证据**，不含编年叙事（那些在 git log 与 `.claude/` 账本）。

用户原话（逐字）：

> 命座掉伤害是因为台阶跳变，这个我需要做一个专项。一个命座水平在难度曲线上覆盖一段 y，
> 加命座会把 y 区间上移，但是区间有重合，特定的某个 y1 可以找到更低的 y2。这就是副作用的由来。
> 我想玩家看命座肯定想看这种客观的区间提升，而不是取两点发现命座说伤害提升了但计算器算出来是负的。

要回答三件事：① 「取两点」为什么会产生负值；② 「区间提升」到底是什么量、怎么算；③ 负值里有多少是
台阶跳变（可解释、不该改数），有多少是**引擎缺陷**（必须修）。

## 1. 结论先行

| # | 结论 | 证据 |
|---|---|---|
| ① | **两级曲线的点根本不是同一批难度**（点数/域都不同）⇒ 「同名档逐点比」连「同一点」都对不上 | §2.1 |
| ② | 即使把两级曲线拉到**同一固定网格**，「同难度比伤害」在中低难度端**全部为正**（+0.88% ~ +7.52%），负值只出现在**高难度端** | §2.2 |
| ③ | **命座本身是正提升（+1.1%~+2.1%）**：那 −12% 全部是 C3 多拿的一份白送 | §3.0 |
| ④ | 白送 = `[表]` 直读在**模块沉默**时按满倍率免费接管（不花闪能、不占时间） | §3.1 |
| ⑤ | **源头**：同一轮里「轴内几窗」有三个数——计划窗 0.137（nec 余量）/ 执行集合 5 / 伤害覆盖率 5。模块读最小的那个⇒沉默；系统用另外两个出伤。`allocateAxisWindows` 的窗口数入参**只统一了一半** | §3.2 / §3.3 |
| ⑥ | 三条修法臂实测：A 去 `backed` 门 = 重复计伤；B 模块读执行集合 = **+1.95%（正）**、白送退场并付代价；C `wins` 取整 = 逐位相同（非载体） | §3.4 |
| ⑦ | **「区间提升」口径成立**：一个命座水平 = 一条 `(难度 x, 伤害 y)` 前沿；比的是两条前沿（同难度比伤害 / 同伤害比难度），不是各自的最优点 | §4 |
| ⑦ | 修法需要一条**口径裁决**：`[表]` 直读「模块沉默就白送」这条是否保留。实测里 A 臂会重复计伤，**B 臂是唯一自洽解**（两套账合一）⇒ 本文给出证据与判据，**未擅自改引擎** | §5 |

## 2. 实测

夹具：`yixuan-jufufu-lucia` / `yixuan-roxy-lucia` / `yixuan-trigger-lucia`（主 C 都是仪玄 1371，槽 0），
探针 `.zc/perf/cinema*.perf.ts`，跑法 `npx vitest run --config .zc/perf/vitest.perf.config.ts <探针>`。

### 2.1 两级曲线不是同一批点

`climbDifficultyLadder` 逐队收敛出的落点（`cinemaNegativeWhere.perf.ts`）：

| 队 | C3 落点 | C4 落点 |
|---|---|---|
| `yixuan-jufufu-lucia` | x=0 / 3.5 / 6.9 / 29.6 | x=0 / 2.9 / 6.9 / 29.6 / 38.1 |

同一支队的相邻两级**点数不同、x 也不同**。于是「同名档逐点比」（页面现行的 `cinemaUplift` 口径：
只变命座、其余全同）在这条曲线上**根本没有可比对**——它比的是「C3 的第 3 点」与「C4 的第 3 点」，
而这两个点落在不同难度上。这就是用户说的「取两点」的第一层副作用。

### 2.2 固定网格上重采样后，负值只剩高难度端

在**同一批 `(parry, dodge)` 网格**上采两条前沿（`cinemaFrontier.perf.ts`，取累积最大 y 的上包络），
再按「同难度比伤害」（C_hi 在 `x' ≤ x` 内的最高 y）逐点比：

| 队（C3→C4） | 同难度比伤害逐点 | 最差 | 最好 |
|---|---|---|---|
| `yixuan-jufufu-lucia` | x=0 **+1.85%** / x=3.5 −2.98% / x=6.9 **+2.51%** / x=29.6 **−11.79%** | −11.79% | +2.51% |
| `yixuan-roxy-lucia` | +2.89 / +2.88 / +2.83 / +0.88 / +2.75 / +2.82 / **+7.52** / −2.07 / −2.88 | −2.88% | +7.52% |
| `yixuan-trigger-lucia` | +2.72 / +2.69 / +3.50 / +2.60 / +2.58 / +2.25 / −1.88 / **−9.80%** | −9.80% | +3.50% |

⇒ **负值不是「区间重合」的必然产物**：低到中等难度上 C4 稳定更好；负值集中在**难度域的最高端**
（x=24~30 一带，正是 C3 拿到幻影行的位置）。所以「区间口径能把负提升洗掉」这个假设**被证伪**——
洗不掉的 3 个点是一条真缺陷。区间口径仍然要上（§4），但它不是用来掩盖负值的。

### 2.3 高难度端到底发生了什么

同一 (parry=20, C3/C4) 的伤害池行（`cinemaBacked.perf.ts`）：

| 命座 | 凝云术 1371022 | 墨烬影消 1371026 | 来源 |
|---|---|---|---|
| C3 | **×15** = 3.46M | **×15** = 1.21M | `轴内·技能表直读` |
| C4 | ×1 = 0.53M | ×1 = 0.18M | 模块行 `1371022` / `1371026` |

其余执行数**完全一致**（`ex=15`、`ult`、前台时间、轴窗 5），伤害却差 4.31M —— 差额几乎全在这两行。

同时读闪能账（`cinemaAlloc.perf.ts`）：

| parry | C3 墨痕化形 #1 / 凝云 | C4 墨痕化形 #1 / 凝云 |
|---|---|---|
| 16 | 14 / **15** | 12 / **2** |
| 20 | 15 / **15** | 14 / **1** |

⇒ C3 的 15 次凝云**不花闪能也不占时间**（直读行「不占时间预算、窗内不产失衡值」是引擎既定口径）；
C4 的 1 次是要付 60 闪能的真循环。两条曲线因此不可比。

## 3. 根因：**「模块沉默」本身有价**

### 3.0 先算清楚：**命座并没有掉伤害，是 C3 被抬高了**

把伤害池里 `轴内·技能表直读` 的行**原价扣掉**（只做算术，不重跑资源链），三支队 C3→C4：

| 队 | C3 原值 | C3 虚高占比 | C3 洁净值 | C4 原值 | 原值 Δ | **洁净 Δ** |
|---|---|---|---|---|---|---|
| `yixuan-jufufu-lucia` | 36.600M | **4.671M / 12.76%** | 31.929M | 32.286M | −11.79% | **+1.12%** |
| `yixuan-trigger-lucia` | 29.442M | **3.429M / 11.65%** | 26.013M | 26.556M | −9.80% | **+2.09%** |
| `yixuan-roxy-lucia` | 26.032M | 0（无表行） | 26.032M | 26.531M | +1.91% | **+1.91%** |

⇒ **命座是正提升（+1.1% ~ +2.1%），一切正常**。那 −12% 全部来自「C3 有一份 C4 没有的白送」。
这不是「命座把伤害削了」，而是**测量把 C3 抬高了 12.76%**。

⚠ 洁净 Δ 是**算术剥离**（把白送行减掉），不是重跑资源链的下限——真实重跑要连白送腾出来的闪能一起收回去，
数字会更高（§3.4 的「同源臂」：+1.95%）。

### 3.1 白送是什么：`[表]` 直读在模块沉默时**按满倍率免费接管**

`resourceCalc/axisTableDirect.ts#axisTableDirectMove` 判据 ② 按 moveId 的**存在性**判
（`backed = Set(executions.moveId)`，不看条数）。于是：

| | 模块有没有产 1371022 的行 | `[表]` 直读 | 实际结算 |
|---|---|---|---|
| **C3** | **0 行**（沉默） | **成立** | 凝云×15 = **3.46M**，**不收闪能、不占时间**、窗内不产失衡值 |
| **C4** | 1 行（静心强制 cloudOut ≥ 1） | **关闭** | 凝云×1 = 0.53M（要付 60 闪能的真循环） |

同一招、同一份轴计划（执行集合都是 `1371022×15`），一份收 0 代价、一份收全额代价。
**「不产行」在这个体系里是收益**——这就是负提升的全部来源。

### 3.2 模块为什么沉默：计划窗 0.137 是**容量余量**，不是物理窗数

`yixuan.ts#applyYixuanTeamConfig`（converge）用 `forEachSlotAxisAction` 数轴内块：
`act.count × axis.windows[ai]`。而 `axis.windows` 在同一次 converge 里是**计划值**，
它被 `solveTeam` 的「非失衡时间充足性约束」按住：

```
nonStunTime = effTime − next × W  <  Σ necessaryTime
  ⇒ next = (effTime − Σnec) / W          // solveTeam.ts 的 nec 约束
```

实测（`cinemaNecPressure.perf.ts`，`yixuan-jufufu-lucia` / parry=20）：

| 命座 | 池窗（`stunPool.stunCount`） | W | Σnec | (eff−Σnec)/W | 计划窗 |
|---|---|---|---|---|---|
| C3 | **5.000** | 19.0 | 177.40 | **0.137** | 0.1369 |
| C4 | **5.000** | 19.0 | 176.21 | **0.199** | 0.1994 |

- `1 块 × 0.137 窗 = 0.137` → `positiveWholeCounts` 向下取整 → **丢弃** → `cfg.yixuanAxisEx` 里 1371022 = 0；
- 而**同一轮**的执行集合用的是 `threads.prevPoolStunCount ?? countStun` = **5 窗** → `actionCountsBySlot = 1371022×15`；
- 伤害侧也按池结算：`stunCoverage = 5 × 19 / 180 = 0.5278`（实测读数逐位吻合）。

⇒ **同一轮里，「轴内几窗」有三个数**：计划 0.137 / 执行集合 5 / 伤害覆盖率 5。
模块读到最小的那个，于是沉默；系统用另外两个数出伤。

### 3.3 源头：这两个数为什么能同时存在

`convergence.ts` 同一轮里 `allocateAxisWindows` 被调用多次，**窗口数入参不统一**：

| 用途 | 窗口数入参 | 位置 |
|---|---|---|
| 决算截断 / `axisInSeconds` / 派发给模块的 `axis.windows` | `stunCount`（**计划**，0.137） | `convergence.ts` 的 `winAlloc` / `axisInSeconds` / `axis.windows` |
| 轴栈执行集合（`actionCountsBySlot` / `axisUltimateTotal` / 合轴节省） | `threads.prevPoolStunCount ?? countStun`（**池**，5） | `calcStunAxisStack` 的 `stunCount` |

后者有一行**写明了理由**：「轴块是『块 × 窗』的整数执行……与雨果决算行及伤害侧栈同源」。
前者（派发给模块的 `axis.windows`）没有跟着改——**同源纪律只落实了一半**。

这就是「两套账」的最底层形态：不是两个模块各算各的，而是**编排层给同一个量喂了两个输入**。
只要计划窗 < 1（实测 `yixuan-jufufu` 0.137、`yixuan-trigger` 0.353），模块必然沉默；
而池窗 ≥ 4，系统必然按 4~5 窗出伤。**沉默是结构性的，不是偶然**。

### 3.4 三条修法臂（都实测过）

| 臂 | 做法 | parry=20 C3 / C4 | Δ | 性质 |
|---|---|---|---|---|
| 现状 | — | 36.60 / 32.29 | **−11.79%** | 白送 12.76%，C4 没有 |
| A 去 `backed` 门 | 让表行与模块行共存 | 43.22 / 43.58 | +0.8% | ❌ **重复计伤**（同一招算两遍，比现状还高） |
| B 模块读执行集合 | `yixuanAxisEx` 改读 `axis.actionCountsBySlot`（与般岳同源） | 34.78 / 35.46 | **+1.95%** | ✅ 两套账合一，白送退场并**付代价** |
| C `wins` 取整 | 对 `axis.windows` 做 `ceil`/`round` | 与现状**逐位相同** | 0 | ❌ 不是载体（`act.count × wins` 的小数是被 `positiveWholeCounts` 按记录丢的） |

B 臂的绝对变化：**C3 36.60 → 34.78（−5.0%）**。这不是退步——那是把白送的 15 次凝云换成
**要付 900 闪能的真循环**（实测同臂 C3 墨痕化形 #1 从 15 次掉到 3 次，闪能全给了凝云）。
$$`[表]` 该不该免费这一问，B 臂给的答案是「不该」**。

## 4. 「区间提升」口径（用户要的客观量）

### 4.1 定义

一个命座水平在难度曲线上不是**一个点**，是**一条前沿**：

```
前沿(C_n) = { (x, y) : x = 操作难度, y = 该难度下的最高伤害 }
```

实测采样后取 **累积最大 y 的上包络**（只有包络才是「这条命座水平的上限」，散点是网格噪声）。
比较两条前沿有两种等价读法，**都必须给**：

| 读法 | 定义 | 回答的问题 | 符号 |
|---|---|---|---|
| **同难度比伤害** | 对 C_lo 的每个 x，取 C_hi 在 `x' ≤ x` 内的最高 y | 「同样的操作难度，加了命座能多打多少」 | Δy ≥ 0 才叫提升 |
| **同伤害比难度** | 对 C_lo 的每个 y，取 C_hi 达到 y 所需的最小 x | 「打出同样的伤害，加命座能省多少操作」 | Δx ≥ 0 才叫提升 |

### 4.2 三条判据（写进实现时按这个判）

1. **不能拿各自的最优点比**：`max y(C_hi)` 对 `max y(C_lo)` 是「两条曲线的端点比端点」，
   端点落在不同 x 上 ⇒ 正是用户说的「特定的某个 y1 可以找到更低的 y2」。
2. **必须披露 x 域重叠**：两级的 x 域不同（§2.1），域外只能单向报（「C_hi 在这个难度上够不到」= 未定义，
   不是 0、也不是负）。
3. **负值必须能被追问到行级**：区间口径仍可能给出负值（§2.2 的 −11.79%），此时页面/专项必须能下钻到
   「哪一行少了几个」，否则读者只能猜是台阶还是 bug。

### 4.3 与现有实现的关系

- `composables/cinemaUplift.ts#analyzeCinemaUplift` = **单场景逐级**（锁失衡次数、只变命座）——
  它是「同一点上的两点比」，**不是区间比**；本文不主张替换它（它是「死数据自检」的检测器，
  AGENTS 规则 5 依赖它），而是**并列**一条区间口径。
- `composables/cinemaUpliftGrid.ts` 已经承认「命座提升率不是角色的内禀属性」（多锁值 / 多 Boss / 多 buff），
  区间口径是同一个思想的第三个维度：**多难度**。
- 数据来源必须是**阶梯**（`difficultyLadder#climbDifficultyLadder`）或**固定网格**；
  只取首尾两点会退回到 §2.1 的缺陷。

## 5. 修法（**B 臂是唯一自洽解**；落地需一条口径裁决）

### 5.1 推荐：模块计数改读**执行集合**（B 臂）

`yixuan.ts#applyYixuanTeamConfig` 的轴内块计数从 `forEachSlotAxisAction`（`axis.windows` = 计划小数）
改读 `axis.actionCountsBySlot[slot]` —— **与般岳同源**（`banyue.ts` 的 `cfg.banyueAxisEx = axis.actionCountsBySlot[slot] ?? {}`）。

实测（parry=20，`cinemaPinWins.perf.ts` / `cinemaExecutedCounterfactual.perf.ts`）：

| 队 | C3 | C4 | Δ |
|---|---|---|---|
| `yixuan-jufufu-lucia` parry=20 | 36.60 → **33.07** | 32.29 → **33.61** | −11.79% → **+1.63%** |
| `yixuan-jufufu-lucia` parry=16 | 35.56 → **31.94** | 31.64 → **32.49** | −11.02% → **+1.72%** |
| `yixuan-trigger-lucia` parry=20 | 29.44 → **26.88** | 26.56 → **27.31** | −9.80% → **+1.60%** |
| `yixuan-trigger-lucia` parry=16 | 25.43 → **25.67** | 25.79 → **26.10** | +1.42% → **+1.68%** |

**会动的数字**：仪玄在所有轴队在**高交互档**下的伤害（C3 侧最大 −5.0%，因为白送退场）。
⇒ 按规则 10 跑 `timeGolden` / `timeFillRatchet` 并逐队归因。

**代价 / 风险**：
- 仪玄从此与「计划口径」的另几家（春正/朱鸢/希格/伊德海莉/比利）不同源——但那几家的白送风险相同，
  这是**逐家暴露**而不是破坏分工；`stunWindows.ts` 头注释本就写明「读哪一个是各模块的产品口径」。
- 需要一条判据防止回退（见 5.3）。

### 5.2 同时要堵的：`[表]` 直读的**存在性门**

即使 B 臂让模块产行，`backed` 门仍会把「模块只表达了一部分」的招式整体交给模块。
B 臂落地后仪玄不再沉默，这条门对它是安全的；但对**任何未来在低计划窗下沉默的模块**，
白送会立刻复现（同一形态，不同角色）。⇒ 建议把判据改成**按条数认领**：

> 模块对某 moveId 有执行行时，`[表]` 只补「轴计划数 − 模块已表达数」；为 0 时不补。

这需要模块上报「轴内表达了多少」——B 臂落地后 `actionCountsBySlot` 就是那个数，
所以 5.1 是 5.2 的前提。

### 5.3 判据（落地后必须绿）

1. **不得再出现「模块 0 行 + 表行 × N」**：某 moveId 的池行里，若 `[表]` 行存在，
   则该槽的执行集合在**同一轮**里该 moveId 的次数必须为 0（现状 C3 违反：表 15 次 vs 执行 15 次）。
2. **同一轮「轴内几窗」只有一个数**：`axis.windows` 派发值、`actionCountsBySlot` 的窗口基数、
   伤害侧 `stunCoverage` 三者必须可互相推导（现状：0.137 / 5 / 5）。
3. **反空洞**：上述判据在「计划窗 ≥ 1」的队上必须同时成立（否则是恒真）。

裁决点只有一个：**`[表]` 直读在模块沉默时该不该白送？**
实测答案倾向「不该」——它让「不实现」比「实现」更值钱（C3 比 C4 高 12.76%，
代价是同一招不收闪能、不占时间）。

## 5.4 已落地（2026-11-04 第二轮，用户裁决「我肯定选真实计算」）

**源头修复（不是模块补丁）**：`convergence.ts` 引入**单一事实源**
`axisWindowCount = threads.prevPoolStunCount ?? countStun`，让三处同源：

| 用途 | 修复前 | 修复后 |
|---|---|---|
| 派发给模块的 `axis.windows` | `countStun`（计划小数 **0.137**） | `axisWindowCount`（池整数 **5**） |
| 轴栈执行集合 | `prevPoolStunCount ?? countStun` | 同一变量 |
| 伤害侧 `stunCoverage` | 池 | 不变（本来就对） |

## 5.6 已落地（2026-11-04 第三轮）：真因是**搜索上界拿 `nec` 当常量**

> 交接文档（§5.5 的原始写法）把它归因为「`pickOuterCycleMember` 交付了坏成员」。
> **逐轮实测否定了这个归因**：交付走的是 **kStar 结算**（`capacityResolved`），不是环内选点。

### 真因

`solveTeam.ts` 的搜索上界：

```ts
const necUsed = out.resourceResult.characters.reduce((s, c) => s + c.timeAllocation.necessaryTime, 0)
const searchMax = min(floor(eff/W), budgetHasRoom ? ceil((eff − necUsed)/W) : floor(eff/W))
```

`necUsed` 取的是**环内选点那一个成员**的必要时间，公式假设「`nec` 与 K 无关 ⇒ 窗口余地 = (eff−nec)/W」。
**该假设为假**，`nec(K)` 随 K 变化且**非单调**（本格 W=21 / eff=180）：

| K | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| `nec(K)` | 176.0 | 181.8 | 179.9 | 178.1 | 177.6 |

环里选中的正是 **K=1** 那轮（它报 `nec=176.0`）⇒ `ceil(4/21) = 1` ⇒ `searchMax = 1`
⇒ 成员扫描只看得见 K=1 ⇒ kStar=1 ⇒ 交付 24.66M。而环里**本来就有** K=2（cont=3.20、net=180.0）
与 K=3（cont=2.92、net=180.0）两个**自洽且装得下**的成员。

## 5.7 已落地（2026-11-06）：交付点 = 前沿点 + 同窗数对照

用户 2026-11-06 口径（逐字）：「用户可能想要的是当前情况的一个确切值」；
「只兑现/兑现率」这类词被否。⇒ 命座提升率要给出**一个确切值**，并配**同条件对照**。

### 病灶（不是「max-K ≠ max 伤害」，而是**候选集被砍**）

OPEN-ITEMS 记的那条「max-K ≠ 最大伤害」在本次全库实测下**没有复现**——
**可行集内部**「K 越大伤害越高」零例外（105 预设 × p∈{0,16} × C∈{0,1} = 210 对，
`.zc/perf/ruleCmp.probe.perf.ts`）。真正的分歧在**候选集边界**，具体是两处：

1. **`auto-1591-1481-1211` p16**：C0 的可行 K 是 K0..K3（K4+ 净占用 193s 装不下），
   **C1 的可行 K 只有 K0/K1**（K2+ 净占用 191s 装不下），而 C1 的**自由收敛停点**在 K3
   （净占用 179.54s —— plan ≠ pin，同一个 K 名下的两个不同点）。
   ⇒ 拿「各自可行集的最大 K」当交付点：C0 → K3 = 32.94M，C1 → K1 = 26.66M = **−19.06%**。
   **这就是用户说的「命座说提升了，计算器算出来是负的」的精确形态。**
2. `yixuan-roxy-lucia` p16 的 C1 只有 K0/K1 可行（K3 净占用 201.87s），同一机制。

### 修法

`composables/cinemaUpliftFrontier.ts#pickDelivery`：候选集 = **收敛停点 ∪ 全部自洽可行钉 K 点**，
交付 = 伤害 argmax（同伤害取小 K）。可行 = **自洽**（`floor(连续失衡) ≥ K`）**且**
**装得下**（`net + 待装补齐 ≤ 有效时间 + 2s`，与 kStar 结算/轴退化/非轴降配**同一把尺**，
单一来源 `solveTeam#netFitsBudget`）。

**关键洞察：收敛停点必须留在候选集里**。它不是「引擎已经对了吗」的装饰——它是唯一能表达
「plan（计划窗）≠ pin（钉住的 K）」这种形态的载体：C1 的收敛停点 37.01M 在**任何**钉 K 上都不存在
（钉 K3 是另一个点：40.12M 但净占用 201.87s 装不下；钉 K1 是 26.66M）。
把它排除 ⇒ 交付点从 37.01M 掉到 26.66M ⇒ 造出本来不存在的负值。

### 原解释（供交接，已带上述限定）

并行会话的判断是「外层把 K 选歪了」。**对了一半，但根因更深**：顺着这条线索查到的形态是
「**同一个 K 名下有两个不同的计划**」——K 本身没歪，是 K 单独**不能标识评估点**。
（该形态在**投影 off 口径**下稳定复现；生产默认口径下 C2 那 7.7% 消失。）

实测格 `auto-1431-1481-1491` C1→C2（p0，预设默认交互）：

| | C1 | C2 |
|---|---|---|
| 收敛停点 | K2 / 30.40M | K1 / **29.78M** |
| 交付点 | K1 / 30.50M | K1 / **32.07M** |

⇒ 收敛口径 C1→C2 = **−2.05%**（并行会话报的那类负值）；交付口径 = **+5.15%**。
这一格的负值**同时含两种成分**：ⓐ K 落点漂移（K2→K1）；ⓑ **同一个 K 内的计划分支漂移**（见下）。
两者必须分开看——只治 ⓐ 修不掉它。

**C2 那 7.7% 的差与 K 无关**——把 K 钉在 1（= 它自己的收敛 K）重算：

| | 收敛停点 K1 | 钉 K1 |
|---|---|---|
| 伤害 | 29.78M | **32.07M** |
| `nec`(1431) | 119.3 | 130.2 |
| 大招(1431) | 4 | 5 |
| 覆盖率 | 0.100 | 0.067 |
| Σ净占用 | 180.00 | 177.99 |

两条路径（「按上一轮池排 K 窗」⇄「按 K 钉住重排」）在**同一个 K** 上给出两个计划，
收敛不动点落到了较差的那个分支。

### ★ 11-07 补上的关键前提：这两条路径**不在同一个投影口径下**

`scanKFrontier` 的「钉 K」是用户锁（`enemy.stunCountLock = K`），而 `useResourceCalc` 在锁定时会
**把 `stunPlanProjection` 从 physical 改成 off**（CC-151：physical 读的是**上一轮池**，会把锁定值旁路掉；
`solveTeam#evalLocked` 同样自己回落 off）。所以：

| 帧 | 投影 |
|---|---|
| 收敛停点（`lock = -1`） | 配置口径（生产 = **physical**） |
| 钉 K 点（`lock = K`） | **恒 off** |

⇒ 「同 K 两计划」的实测差 = **计划分支差 ⊗ 投影口径差**，两个成分在本探针里**分不开**。
这也正是 physical 下差消失的原因：physical 的计数通道已经读物理次数（= 锁定值），
两侧的**计数**口径被拉平了，只剩时间账那一侧还可能分叉。
**不要把「physical 下差小一个数量级」读成「计划分支问题被物理投影治好了」**——
它只是让这个探针看不见了。

**全库量级**（`.zc/perf/sameKGap.probe.perf.ts`，105 预设 × C0/C1/C2 = 315 格，**未过滤可行性**）：
|收敛停点 − 钉同 K| **48 格 > 5%**、**9 格 > 10%**、最差 **51.5%**（`banyue-liuyin-lucia` C2）。
过滤掉「装不下」的点后是 **39 格 > 5% / 4 格 > 10% / 最差 24.0%**（见上方纠正①的表）。

同时核对：收敛停点**自洽性**没问题（420 格零例外 `floor(连续失衡) ≥ 池窗`，`.zc/perf/selfConsist.probe.perf.ts`）
⇒ 不是「按 K 排了窗、池却撑不住」那类缺陷（那类已被 CC-150/153 的 `feasible` 判据挡住）。

⇒ 本卡把它**吸收进交付点**（不是修那个分支不动点）：判据 `cinemaUpliftFrontier.test.ts` ⑤ 钉住
「同 K 名下的两个计划必须被交付点纠正」，含反空洞（C2 交付 K 仍是 K1 ⇒ 漂移发生在同一个 K 内）。
**根治**（让收敛不动点选对分支）是另一张卡：要先判定「两条路径哪个才是该配置的规范计划」，
那是 `solveTeam` 的环内选点 + 补齐线程口径，不属于本卡。

### ★★ 11-07 裁决：「钉 K 分支是规范计划」**不成立**——装不下的钉 K 是透支，不是计划

原闸门 B 的前提是「钉 K 分支（`evalLocked`）的计划才是该配置的规范计划」。**实测证伪**：

`banyue-liuyin-lucia` C0（全库 physical 口径最差的那格，+22.2%）：

| | 收敛停点（K3） | 钉 K3 |
|---|---|---|
| 伤害 | 24.83M | **30.34M（+22.2%）** |
| 计划失衡 / 池次数 | 3.000 / 3.000 | 3.000 / 3.000 |
| **Σ净占用** | **179.75s** | **247.06s**（有效 180s） |
| 大招（1471/1481/1451） | 7 / 3 / 2 | 11 / 4 / 4 |

⇒ 钉 K3 的计划**多排了 67s 前台动作**。那不是「同一 K 上更优的计划」，是**时间账装不下**的透支；
它报的 30.34M 在 180s 里打不出来。`scanKFrontier` 已经把它判成 `fits=false ⇒ feasible=false`，
**排除在交付候选集之外**——所以「交付点 = 前沿点」那条口径本身是对的，
错的是**把不可行点也算进漂移普查**（`gapBoth` / `sameKGap` 两个探针都没过滤）。

**结论**（三档，别再混）：
- 装不下的钉 K 点 ⇒ **不是计划**，任何「同 K 漂移」统计都必须先过滤（physical 口径 315 格里 4 个、off 口径 16 个）；
- 装得下的钉 K 点 ⇒ 是**真实可达的操作点**，且在 47/315（physical）格上**高于**收敛停点，最大 8.0%
  ⇒ 这是「外层不动点收敛到自洽点、但不是该 K 上伤害最大的点」的**搜索松弛**，由交付点吸收；
- 收敛停点 ⇒ 引擎自己真的到达过的那一帧，保留在候选集里（排除它会造出本来不存在的负值）。

⇒ 原闸门 C 的处置**生效**：「该形态在 physical 口径下仍存在」只成立到 **4 格 >5% / 0 格 >10% / 最差 8.0%**，
优先级 P1 → **P2**；且 off 口径那些残留**确实只在难度曲线**（`clearDifficultyLevers` 的唯一生产调用方是
`difficultyCurve.ts`；队伍对比 / 命座提升率页都走生产默认 physical）。
**根治仍待办**（不动点不保证伤害最优，47 格 ≤8%），但它要改 `solveTeam` 的 stable 退出路径
（在 kStar 结算之外也试一次 `evalLocked(kStar)` 取大者），会大面积动 `timeGolden` ⇒ 单独立卡。

用户口径（2026-11-07）：「−0.03% 这种如果他是主c就不合理，他自己的属性区都有十几的提升」。

**实测反证**（`.zc/perf/panelVsMove.probe.perf.ts`，同一角色仪玄 1371 在 `auto-1371-1481-1451`）：

−0.03% 那一级（C2）**面板零变化**——它是「加一个新招式行、抢 7.9s 平A 时间」的**资源权衡**：

| 槽 | 伤害 Δ% | 强特 | 大招 | 平A 时间 |
|---|---|---|---|---|

所以不是资源账出错，是**平A 池在三个人之间重新分配**。
净效果：主 C +0.299M，两个辅助 −0.183M / −0.123M ⇒ 全队 −0.03%。

⇒ **这不是缺陷，是「加动作 ⇒ 抢时间」的真实物理**；但它暴露了一个**展示层问题**：

   「后一级的交付点不得低于前一级」。**这是可修的**（候选集加一条「不低于前一级交付点」的下界，
   或两级用同一 K 的 argmax 做交叉校验），但要改交付规则 ⇒ 按硬约束 5 留待裁决。
2. 其余 4 条（含 K 相同的 −3.80%）是**真实物理**：命座加的动作挤掉了更值钱的行

## 5.9 追加核查（2026-11-07 第六轮）：**尾窗残疾不在这两格里**，但「K 越大越攒不出」被量到了

### ② 这里的成因是「第 3 窗根本没开」，代价是**整整一窗**

### ③ 挖到一条新事实：**同一配置，K 越大攒得越少**（且跨过了可行线）

### ★ ⑥ 连续失衡的实现现状（2026-11-07 第六轮审计）——**只有一条腿真的在跑**

用户口径（2026-11-01 裁明机制）：失衡只有两态；满条开窗遇上「非失衡攒条时间 + K×W > 180s」时，
**溢出从最后一窗的时间里丢弃**（时钟截断），随击破效率提高溢出收敛到 0 即成为完整窗。

「连续失衡」在本仓有**四条互不相交的实现**，现状：

| 腿 | 代码 | 现状 |
|---|---|---|
| ① 攒条侧：连续计数 | `core/stunPool#continuousStunCount` | **活的**，`scanKFrontier` 的可行性判据用的就是它 |
| ② 攒条侧：缺口标注 | `core/continuousStun#continuousStunProgress` | **活的**（难度曲线/队伍对比页文字），但**零求值影响**（§33 裁决） |

### 「连续」到底连续在哪：**时间连续，攒条不连续**

- **时间侧是连续的**：`decomposeStunWindows` 能给出「第 n+1 窗只分到 room 秒、完成率 room/W」——
  这是真正的「尾窗残疾」。它的触发条件是 `K×W > effTime`，与攒条侧完全无关。
- **攒条侧是离散的**：`floor(cont)`，差 0.0004 窗与差 0.99 窗同结果（§5.9 ⑤ 的 494 个近失点全部如此）。
  用户 2026-10-21 §33 明确否决过把小数当窗（当年实测 86/93 队 `cont` 带小数 ⇒ 覆盖率虚高、8 条判据红）。
- ⇒ **两个「不连续」是两条独立的轴**：本卡那 2 格卡在**攒条轴**（`K×W = 75s ≪ 180s`，时间轴无事发生）。

### 为什么当前这条腿几乎不跑（结构原因，不是没接）

`solveTeam.ts:478` 的 `physicalMax = floor(effTime / W)` 把搜索上界封在「时间刚好装得下几个整窗」。
于是交付的 K 恒满足 `K×W ≤ effTime` ⇒ **时钟截断的触发条件本身被排除**（K+1 窗根本不会被计划出来）。
A10 两趟（`PROBE_STUN_CLIP_ITER`，缺省开）只负责「把**装配期**溢出（必要行装不下 ⇒ `overflowSeconds`）
记到末窗上」——那是**动作排不下**的溢出，不是「第 K+1 窗攒满了但 180s 装不下」的溢出。
两者在读数上共用 `overflowSeconds` 这个字段，所以 A10 看起来像在跑连续失衡；**实测 11/315 格有值**。

⇒ 要真正打开「攒满第 K+1 窗但装不下」的那种连续失衡，得做 A10 四步（`docs/mcp-cinema-interval-uplift.md` §5.7
引的 `TASK-continuous-stun.md`）：① 池可超 `physicalMax` ② 排被截短的末窗 ③ 覆盖率扣截断秒 ④ 展示读时间轴。
①③④ 已有零件，**缺的是 ②**——而现在 `physicalMax` 那一行正好把 ① 挡在门外。

### 与用户追问的关系

「3.01 vs 2.96」是**攒条轴**上的门槛抖动（差 0.062 窗），不是尾窗残疾；尾窗残疾要走时间轴，而这两格
时间上宽裕（75s ≪ 180s）。⇒ 那 2 格负值的解释**不依赖**连续失衡的兑现层，依赖的是 `floor(cont)` 这一刀。

### ★ ⑦ 「两者能保全吗」——能，因为**引擎本来就吃小数计划窗**（实测）

`stunWindowFraction(plan, W, eff) = min(1, plan·W/eff)` 对 `plan` **不做 floor**。把 `stunCountLock` 直接喂小数，
覆盖率与伤害都按比例兑现（`.zc/perf/fractionalPlan.probe.perf.ts`）：

| plan | `auto-1501-1511-1491` C4 覆盖 / 伤害 | `banyue-roxy-lucia` C2 覆盖 / 伤害 |
|---|---|---|
| 2 | 27.78% / 29.022M | 22.22% / 25.036M |
| 2.5 | 34.72% / 31.501M | 27.78% / 27.297M |
| 2.958 | 41.08% / 34.003M | 32.87% / 27.900M |
| 3 | 41.67% / 34.699M | 33.33% / 28.278M |
| 3.2 | 44.44% / 35.602M | 35.56% / 29.673M |

覆盖恰好 = `plan × W / eff`（2.5×25/180 = 34.72% 逐位对上），伤害随 plan 单调。
⇒ **兑现侧不需要新机制**；缺的是「谁来决定那个小数」。

### 因此冲突不在「连续失衡 vs 物理上限」，而在**一个数被当了两用**

| 用途 | 该用哪个量 | 现状 |
|---|---|---|
| 搜索上界（别去搜不可能装下的 K） | `floor(eff/W)` | ✅ 就是 `physicalMax`（T180 的成果，防搜索塌陷） |
| 计划窗数上限（第 K+1 窗能不能不满） | **不该用同一个 floor** | ❌ 同一个数被复用 ⇒ 连续失衡被钳掉 |

T180 的证据：上一版用 `nec` 推上界 ⇒ `searchMax=1` ⇒ 只搜到 K=1 ⇒ 交付 24.66M，
而环里本来有 K=2/K=3 两个自洽成员（钉窗实测 28.86M / 31.92M）⇒ **上界塌陷比多搜几次贵得多**。
所以 `physicalMax` 必须留；它该管的是「不要搜 `floor(eff/W)` 以上的**整数** K」。

### 保全两者的形态（尚未落地，需口径裁决）

1. 整数搜索仍以 `physicalMax` 封顶（不动 T180）；
2. 允许「第 K+1 窗不满」的候选：`plan ∈ (K, K + room/W]`，`room = effTime − K·W`（时钟余量）；
3. 小数来源**只能取两者较小值**：`min(时钟余量, 攒条兑现 fraction)`——即「攒得够但时间不够」才算，
   「攒不够」仍按 §33 不给（这条是用户 2026-10-21 的裁决，不能顺手推翻）。

⚠ 对这两格，第 3 条**仍然救不了它们**：它们的 `cont` 缺口是攒条侧的（2.958 < 3），时钟余量充足（105s）。
要让它们转正，只能把口径改成「攒条 95.8% 也按 95.8% 兑现」——那是 §33 的正面推翻，
影响全库 494 个近失点，必须单独裁决，不能夹在交付规则里做。
