## 0. 现状的一句话诊断

这个计算器的**骨架是「整局总量 + 不动点迭代」**：能量、喧响、失衡次数都按 180 秒的总量结算，再在多轮之间迭代收敛（`docs/ARCHITECTURE.md` §1；`src/core/resourceTrack.ts` 头注释原话：「引擎资源结算是『整局总量口径』……不知道第 N 次失衡窗口开启时资源够不够」）。

过去几个月大部分难啃的问题，都是这副骨架的**副作用**，而不是某个角色写错了：

- DEBT 登记簿里现存 6 条，有 4 条直接指向它：「全局实数化收敛重构」「轮换动作覆盖实数化」「截断不回灌资源循环」「克拉蕾残痕总量口径天花板（需要引擎具备逐事件顺序的通道）」（`scripts/lib/guard-registries.mjs` DEBT_REGISTRY）；
- 失衡次数**仍是双源**：池的连续不动点，和外层不动点 `stunCount` 并存（`docs/ENGINE_PIPELINE_GUIDE.md` 表格「失衡次数」行，坑 25）；
- 阶梯 2-循环会产生「失衡 0 次」（坑 25），小数次数会被截断，导致整行消失（坑 36）；
- 两项产品级裁决一直拍不了板：主路径要不要走边际均衡（49 队落点 ±0.4%~±28%）、失衡易伤只兑现两成（信用 0.1966）。卡住的原因是**伤害没有外部真值锚**（坑 35、坑 37；AGENTS.md 第 131 行：实战归档不作误差判据）。

所以，往上游走有两件事：**换骨架**（方向 A），以及**给数字找一个能证伪的锚**（方向 B）。其余三个方向建立在这两件事之上。

## 方向 A · 事件时间轴内核：用离散事件仿真替代「整局总量 + 不动点」

> 🛑 **已否决（2026-09-27）**，依据见 `docs/REQUIREMENTS.md` 文末「R4 撤销说明」（用户提交 `3737419`，2026-09-27 16:47）。前提不成立（收敛法没有本质错误），方法也不可行（需要引擎拿不到的决策信息）。以下内容只作历史记录。

**要解决的根本问题**
- 引擎不知道「事情发生的顺序」。资源是否够放大招、失衡窗口里放了什么、180 秒到点时截掉了哪些动作，全靠总量折算加启发式补丁来近似，再用不动点迭代把各个近似拉成自洽。
- 近似之间互相喂数据，形成了双源（失衡次数）、2-循环（坑 25）和截断不回灌（DEBT）。
- 方向 A 的做法：直接模拟一条 180 秒时间线，按事件推进，包括动作、资源变化、失衡开关窗、buff 上下场、大招。次数就是整数事件计数，天然不会出现小数；截断就是时间线走到终点，天然会回灌。

**为什么是现在**
- 已经有种子：`src/core/resourceTrack.ts`（100 行）是喧响轨的窗口时序模拟，头注释自称「对轴模块第一步」；轴模式（自动失衡轴）已经在做「窗口内/外」的切分。
- 近 90 张 CC 卡把角色特判从 core 里迁进了模块能力（`core agentId` 棘轮为 0，`core 角色模块引用` 为 0）。**只有 core 是纯的，才有可能换掉它**。一年前这件事做不了，现在前置条件已经具备。
- 测试护栏齐全：3714 条测试，还有 timeGolden、零差 dump/rowsnap、allAgentsSweep，可以做「新旧双跑对拍」。

**预期收益**
- 对用户：能回答「第 3 次失衡时大招放不放得出」「这一队哪里卡资源」这类**时序问题**，可以画出真正的时间轴；总量口径永远答不了这类问题。
- 对可维护性：4 条 DEBT 和双源问题会被**结构性消灭**，而不是再逐条打补丁；`CalcRoundThreads` 那套跨轮反馈线程（`resourceCalc/roundThreads.ts`）可以整体退役。
- 对正确性：去掉由不动点收敛引起的伪影（2-循环、截断丢行）。

**风险与不可逆点**
- **全库数值一定会变**，而且没有真值可以判断变得对不对（所以先做 B）。
- 模块能力接口要从「交出总量」改为「对事件做出反应」，62 个模块都要适配。这是最大的工程量，一旦切换，也是事实上不可逆的点。
- 可能更慢：逐事件模拟加 16 个角色组合的扫描，性能需要先做原型验证。

**工作量级：大**，但可以切成可独立验收的刀：
1. 影子内核：新建 `src/core/timeline/`，只做喧响加失衡两条轨，与现引擎**并行运行、只报差异、不接 UI**；
2. 选 3 支队（轴模式已覆盖的那几支）逐位对账，解释每一处差异；
3. 模块能力加「事件钩子」这个可选接口，与总量接口并存；
4. 按队伍逐支切换（功能开关），旧引擎保留到全库切换完成。

**与当前重构的关系**：**不冲突，而且是它的下游**。core 解耦正是方向 A 的前置条件。唯一要注意的是：拆大文件时不要再往不动点线程里加新的反馈字段（例如 `CalcRoundThreads` 新增字段），否则会增加迁移面。

## 方向 B · 可证伪的真值锚：受控实测校准集 + 误差预算

> ⏸ **暂缓（2026-09-27，lead 按 R5 拍板，可逆）**。`docs/REQUIREMENTS.md` R5 的用户口径：「和投稿比较是很后期的事情」「实测结果最终还是用户口述录入，没有增加独立信息」「禁止用更接近投稿当验收理由」。当前阶段以 **R5 规格-实现对账**为准。`docs/mcp-calibration-atoms.md`（CC-97）保留，到用户宣布进入数值对表阶段时再启用。**回退点**：用户若要求恢复实测，删掉本条即可。

**要解决的根本问题**
- 现在所有数值变动都只能证明「与上一版一致」（零差），证明不了「与游戏一致」。
- 用户已经裁决实战归档不作误差判据（幸存者偏差，配装、操作、词条都未知），这个裁决是对的，但结果是**产品级口径永远无法裁决**：边际均衡、失衡易伤回落、方向 A 的全部数值变动都会卡在这里。

**做法**
- 不用投稿，改用**受控实测**：在训练场用固定配装，记录单招单跳伤害、失衡值、喧响回复、buff 持续时间等**局部可观测量**，每一条都附配装快照和录像时间码。
- 校准集按「机制原子」组织，例如「雷暴重金属 4 件套攻击力%的基底」「失衡易伤倍率」「单次碾的能耗」。
- 每个原子对应一个可执行断言，写进 vitest：`引擎局部输出 ≈ 实测 ± 误差预算`。
- 整局伤害仍然不作判据，只校准**原子**。原子都对了，整局的误差就来自编排和时序，那是方向 A 要解决的问题。

**为什么是现在**
- 已经有一批悬而未决、只能靠实测回答的问题，都登记在册：
  - `ENGINE_PIPELINE_GUIDE.md` 第 487 行：「拿到实战视频/游戏内单跳校准数据后……」；
  - `GAME_TERM_TO_CODE_FIELD.md` 第 183、195 行：「游戏内实伤对表一次」；
  - 本轮 CC-96 发现的驱动盘 `basis` 问题：若实测证明是基础攻击力，就要先让引擎认 basis。
- 146 条 `@fact` 口径和 ⟳ 复核触发器已经把「哪些结论依赖游戏语义」标注好了，**校准集的目录几乎是现成的**。

**预期收益**
- 对用户：数字第一次有了「多准」的说法；产品级口径（坑 35、坑 37）可以拿实测来裁决，不必每次都等用户拍板。
- 对可维护性：版本更新后跑一遍原子断言，立刻知道哪些口径失效，比 ⟳ 到期提醒更早、更准。
- 对正确性：把「猜测 / 近似」标签变成有误差条的数字。

**风险与不可逆点**
- 需要人（或人加录像）去游戏里测，**AI 做不了采集**，只能出测量清单和录入格式。这是唯一依赖用户投入的方向。
- 训练场和实战可能存在差异（例如敌人抗性），需要在原子定义里写清楚测量条件。
- 不可逆点：无。校准集只是新增文件，不改引擎。

**工作量级：中**。
1. 出「测量清单 v1」：从 @fact 和 ⟳ 里挑 10–20 个最影响数值的原子，每个写清楚怎么测、测什么、预期落在什么区间；
2. 定录入格式与 vitest 断言框架（`src/calibration/`）；
3. 用户测一批，AI 录入并对账，产出差异报告。

**与当前重构的关系**：**完全不冲突**，可以立刻并行开始。它也是 A 和 D 的前置条件。**唯一需要用户重新裁决的点**：确认「受控实测原子」不属于已裁决「不作误差判据」的范围。我的理解是不属于：那条裁决针对的是投稿归档的整局伤害，而这里是受控条件下的局部量。

## 方向 C · 机制即数据：62 个 TS 模块 → 声明式 spec + 版本更新流水线

**要解决的根本问题**
- 每出一个新角色，都要手写一个 TS 机制模块（现有 62 个，`src/mechanics/agents/`），外加 spec JSON（62 个，`src/specs/agents/`），两套表达并存。
- 模块里是任意代码，只能靠人读和测试兜底；判据 13/14/25 抓的「接了没用 / 用了没接」类静默缺口，根源也在这里：任意代码没有结构可以校验。
- pending 待办仍有 108 项（命座）和 40 项（机制）（`zc status`），多数属于「原文有、代码没有」。

**做法**
- 扩展 spec 的表达力，覆盖 80% 常见机制（条件 buff、叠层、资源转换、额外伤害事件、命座改写倍率）；spec 由通用解释器执行，TS 模块只保留真正特殊的部分。
- 版本更新流水线：nanoka 原文 → LLM 生成 spec 草案 → validate-specs 校验 → 人工与 AI 复核差异 → 合入。现有的 `import-nanoka-*.mjs` 和 `bootstrap-specs.mjs` 是起点。
- spec 可以做**静态分析**：每个 buff 是否有消费者、原文数值与 spec 数值是否对账、命座是否全覆盖。静默缺口从「靠判据事后抓」变成「在 schema 层面写不出来」。

**为什么是现在**
- core 解耦之后，模块能力接口已经收敛（`src/mechanics/types.ts` 已拆分，CC-83），能力面相对稳定，现在可以盘点「哪些能力可以数据化」。
- 已有先例：`specToMechanicModule` 和 spec 资源解释器（`computeSpecResources`）已经在运行，佩洛（1551）是纯 spec 角色（`sync-spec-adjustables.mjs` 头注释）。

**预期收益**
- 对用户：新角色上线更快，版本更新后的缺口清单能自动产出。
- 对可维护性：机制代码量大幅下降；低级模型也能可靠地编写 spec，而改 TS 模块则需要 lead 级理解。
- 对正确性：原文对账可以机器化。

**风险与不可逆点**
- 过度设计的风险：spec 变成一门写得很差的编程语言。**要有退出条件**：某种机制在 spec 里需要超过 N 行的特殊语法，就留在 TS。
- 迁移期两套并存，维护成本暂时上升。
- 不可逆点：spec schema 一旦被大量数据使用，改 schema 需要迁移脚本。

**工作量级：大**，可以切刀：
1. 盘点 62 个模块，按「可数据化 / 部分 / 不可」分类，产出覆盖率报告，纯只读；**✅ CC-98 已完成**（`docs/mcp-mechanic-dataization-census.md`）。**口径已修订**：按能力数分档没有区分度（`buildCharConfig` 61/61 在用），改为数「spec 生成不了的过程类能力」，并把边界定在钩子内部的 4 种原语 G1–G4。第 2 刀因此改为「先给 spec 加原语，再迁模块」；
2. 挑 5 个「完全可数据化」的角色，迁成纯 spec，要求零差；
3. 做流水线 MVP：选一个新角色，从原文到 spec 草案。

**与当前重构的关系**：**弱冲突**。若和方向 A 同时推进，模块接口会被改两次（事件钩子加数据化）。建议 **C 的第 1 刀（盘点）现在就可以做**；第 2 刀以后排在 A 的「事件钩子接口」定稿之后，让 spec 直接对着事件接口设计。

## 方向 D · 从「计算器」到「决策器」：统一的优化与解释层

**要解决的根本问题**
- 仓库里已经散落着好几个求解器：难度阶梯贪心（`difficultyLadder.ts`）、时间权重均衡（`timeWeightBalancer.ts`）、抽卡规划 beam search（`pullPlannerEngine.ts`）、配装子属性优化（`core/substatOptimizer.ts`）、第三人扫描（`teamCompareSweep.ts`）。
- 它们各自为政：目标函数、约束、「为什么是这个解」的解释方式都不统一，用户拿到的是一堆数字，而不是一个决策。

**做法**
- 抽出一个统一的「决策层」：目标（伤害 / 分数 / 性价比）× 决策变量（队伍、配装、轴、抽卡顺序）× 约束 → 求解，并附**敏感度与归因**。归因回答「换掉这个驱动盘，伤害降 X%，其中 Y 来自失衡窗口少了一次」。
- 归因要依赖方向 A 的事件时间线（知道每一点伤害来自哪个事件），而可信度要依赖方向 B。

**为什么是现在**：求解器的数量已经多到值得统一（至少 5 个）；但决策层真正的价值要等 A 和 B 就绪，所以现在只适合**设计**，不适合实现。

**预期收益**
- 对用户：从「看数」变成「得到建议 + 理由」，这是产品形态的升级。
- 对可维护性：5 套求解器合并成一套框架。
- 对正确性：敏感度分析能暴露「数值对某个近似极度敏感」的地方，反过来指导方向 B 该先测什么。

**风险与不可逆点**
- 在数值没有被锚定的情况下给建议，会把误差包装成权威。**必须在 B 之后上线**。
- 性能：统一框架可能比专用求解器慢。

**工作量级：中–大**。第 1 刀：写一份接口设计文档，把现有 5 个求解器映射到统一接口，不写代码。

**与当前重构的关系**：**不冲突**。`TeamComparePage.vue`（1462 行）和 `teamCompare.ts`（1358 行）的拆分正好可以按「决策层 / 展示层」的边界来切。

## 方向 E · 口径即契约：让游戏语义口径与版本号绑定、可执行

**要解决的根本问题**
- 146 条 `@fact` 与 ⟳ 复核触发器是**文字**，到期了靠人（AI）去读、去判断（例如本轮 CC-96 就是逐条手工复算）。
- 游戏版本更新时，没有机制告诉我们「哪些口径因为这次更新失效了」。

**做法**
- 每条口径绑定：数据来源（nanoka 字段路径）+ 可执行断言 + 游戏版本号。
- 导入新版本数据时自动 diff：哪些原文字段变了 → 哪些口径受影响 → 哪些测试需要重看。
- ⟳ 触发器从「日期到期」改为「**依赖的数据变了就到期**」。日期是代理指标，数据变化才是真正的触发条件。

**为什么是现在**：@fact 解析器、drift 检测（`zc drift`：锚点文件变动 → ⟳）、手册复核触发器都已经存在，只差把「锚点」从源码文件扩展到**原始数据字段**。

**预期收益**：版本更新的影响面可以机器计算；复核工作从「逐条读」变成「只看被触发的」。

**风险与不可逆点**：低。风险主要是把 146 条口径全部补上数据锚的工作量；可以只做新增口径和高时效口径。

**工作量级：中**。可以作为 B 的配套一起推进（B 的原子天然就是有数据锚的口径）。

**与当前重构的关系**：**不冲突**，只触及 scripts 和 docs。

## 推荐顺序与理由

> ⚠ **本节已作废（2026-09-27）**：A 已否决，B 暂缓。当前顺序以 `docs/REQUIREMENTS.md` 为准，R5 规格-实现对账排最前。方向 C 第 2 刀原来依赖 A 的事件钩子，这个依赖已经消失；D、E 不受影响。

1. **B（真值锚）现在就开始，与 CC 系列并行。**
   - 理由：它不改引擎、零不可逆点，又是 A 和 D 的前置条件。
   - 瓶颈在用户测量，所以越早出「测量清单 v1」，越早能拿到数据。
   - 第一件事就可以立刻做：列出 10–20 个原子，驱动盘 `basis` 问题排在第一个。
2. **C 第 1 刀（模块盘点，只读）顺手做**：结论会影响 A 的事件钩子接口设计。
3. **A（事件时间轴内核）在 core 解耦收尾后立项，先做影子内核。**
   - 理由：收益最大（结构性消灭 4 条 DEBT 和双源问题），但数值必然变动，最好在 B 有了第一批原子之后再做切换决策。
   - 影子模式期间不影响用户。
4. **E 随 B 一起做**：B 的每个原子天然就是一条带数据锚的口径，顺手把机制建起来。
5. **D 最后**：它的价值依赖 A 的归因能力和 B 的可信度；在那之前只做接口设计。

**如果只能选一个**：选 **A**。它最「颠覆」，也是唯一能把「近似叠近似、再用不动点凑自洽」这一类问题从根上消除的方向。但请同时启动 B 的测量清单，否则 A 切换那天没有依据判断新数字是否更好。
