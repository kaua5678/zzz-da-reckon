## 0. 一页摘要

抽卡价值计算要回答的问题只有一个：

> **在给定账号、给定预算、给定评价期内，多持有这张卡，能让我的最优可行收益提高多少？**

由此推出的五条核心思想：

1. **成本是流，收益是期。** 菲林分期到账、卡在窗口内可买、强度按期结算——三根时轴不能混成一根。
   用"每万菲林兑现多少分"给卡排序，等于把多期约束问题压成单期比值，会系统性偏好便宜的小幅提升。
2. **不抽永远可行。** 任何卡的增量价值下界是 0；而且**可以严格等于 0**——当它是已有选择的完全下位时。
   这不是"算不出来"，是有效且可执行的结论（建议不抽）。
3. **价值必须相对某个持有集。** 同一张卡对新号、成型号、已持有其上位替代的账号，价值不同甚至为 0。
   脱离"相对谁"谈卡的价值没有意义。
4. **零价值有两种，必须分开报。** 一种是**确证的完全下位**（真 0，可信）；
   另一种是**搜索没能发现增益**（0 或负差被截断，只说明本次搜索的证据强度）。混在一起会既误伤真结论、也放过假结论。
5. **单卡 ROI 不是决策变量。** 菲林是共享预算：投给 A 就不能投给 B。决策变量是"同等预算下的最优行动"，
   单卡比值只是诊断读数。

## 1. 现有模型：三种读数，三种身份

仓库里其实并行着三套"价值"，它们回答的问题不同，**不能互相替代、也不该混排**：

| 读数 | 实现 | 它是什么 | 它不是什么 |
|---|---|---|---|
| **历史兑现** | `pullValue.ts` `computePullValue`（Chart 5） | 归档里"同作者同房间带卡 vs 不带卡最佳分差"的中位数，沿时间累计 | 不是因果收益，不是引擎强度，不是未来预期 |
| **引擎强度** | `pullPlannerEngine.ts` oracle（Chart 6 内层） | 固定持有集下，引擎算出的每期 3 房不重叠最优组队分数 | 不是实战可达值（收敛过滤已排除一部分队） |
| **预算约束重规划** | `pullPlanner.ts` `computeCardValuesVcg` | V(全卡可购) − V(禁购该卡重规划)，条件于起点持有集 | 不是 VCG 支付，不是可加总的价值 |

三者的量纲也不同：Chart 5 的分数含操作分（单房上限 65000）；引擎侧的伤害分上限 60000
（`src/data/deadlyAssaultScore.ts`，分段线性，**不是** `60000 × 伤害比`）。
把它们放进同一张表比较，等于拿三种尺子量同一根木头。

## 2. 成本侧：菲林投入怎么算才对

### 2.1 现状

`src/data/filmEconomy.ts` 是成本单一事实源：

- 角色金（本体/影画）期望 **15000 菲林**（93.75 抽 × 160）
- 音擎金（本体/精炼）期望 **10000 菲林**（62.5 抽 × 160）
- 每版本免费收入默认 **25000 菲林**（`PLANNER_FILM_PER_VERSION`，可编辑）
- 充值按性价比固定分配：月卡 30 元→3300 → 大月卡 68 元→≈2600 → 直充 10 菲林/元（`allocateTopUpFilm`）

规划器的购买阶梯（`pullPlanner.ts` `TIER_COSTS`）：
本体 15000 → 专武 10000 → 满配增量 130000（6 影画 × 15000 + 4 精炼 × 10000）。
**满配累计 = 155000 菲林**，不是 12 × 15000。

### 2.2 三条成本口径

**(a) 成本是"期望菲林支出"，不是"金数"。**
金数是展示与归档口径（`limitedGold.ts`：角色本体 1 + 影画 + 限定专武本体 1 + 精炼−1，满配 12），
菲林是预算口径。同一件专武"1 金"但只花 10000——两者不能互相折算。

**(b) 成本必须条件于"从哪一档升到哪一档"。**
从零到本体花 15000；从本体升专武只花 10000；从本体+专武升满配花 130000。
任何"按金数乘一个均价"的折算，都会在升级路径上算错。

> **已落地**（2026-09-29）：`CardValueVcg.spentInPlan` = 该卡在最优轨迹里各次购买成本之和
> （走 `cardValuePer10kFilm()` 取比值），取代原先按档位硬编码的 `tier3?17 : tier2?2.5 : 1.5`。
> 修正面（实机读数：价值 5572 分、投入 2.5 万 → 2229 分/万）：
> - **满配**：旧除 17 万，实际累计 15.5 万 ⇒ 低估 8.82%；
> - **升档路径**：已持有本体再升专武只花 1 万，旧按 2.5 万除 ⇒ 低估 60%；
> - **从零买本体/专武**：旧口径恰好正确（1.5 万 / 2.5 万），本次零变化。
> 分母 ≤ 0 或搜索不自洽时返回 `null`（页面显示「—」），不显示成 0。

**(c) 收入是分期到账的，不是期初一次性给的。**
`pullPlanner.ts` 的 `filmGrants` 按**期日期变化**发薪，而不是按版本 ID 或版本边界。
这意味着：Boss 登场稀疏的版本会少发薪，攒钱速度被"Boss 排期"而非"版本节奏"决定。
收入轴、卡池窗口轴、结算期轴是**三根轴**，理想形态应各自独立（收入按版本日历，购买按首 UP 窗口，结算按期）。

## 3. 收益侧：强度回报怎么定义

### 3.1 主目标应是"固定期限累计分数"

建议把决策目标写成：

```
V(S, B) = max over 策略 π  of  Σ_{t ∈ 评价窗口} score(期 t, 队伍(t), 持有集(t))
s.t.  每期支出 ≤ 银行余额，银行(t+1) = 银行(t) + 收入(t) − 支出(t)
      持有集(t) ⊆ S ∪ {窗口内可购的卡}，且购买不可逆
```

要点：

- **不设折现率（r = 0）**：老卡贬值由每期 Boss 血量/抗性数据自然涌现（现有口径，见 `pullPlanner.ts` 头注释）。
  人为加折现因子等于把"环境膨胀"和"时间偏好"两件事混成一个参数。
- **分数用引擎伤害分**（0–60000 分段线性），操作分不计入强度。
- **主目标是总分最大化，不是 ROI 最大化**。ROI 作为诊断列展示，不参与排序。

### 3.2 单卡价值：条件化的边际

```
Δ(c | S, B) = V(S ∪ {c}, B) − V(S, B)   ≥ 0
```

- **下界恒为 0**：不抽永远是一个可行策略（`pullPlanner.ts` 的"攒着"分支），
  所以"允许购买 c"不可能让最优值变差。
- **条件于 S**：同一张卡在 `S = ∅`（新号）与 `S = {c 的上位}`（成型号）下价值不同。
  这就是"比利 vs 维琳娜"类问题的形式化——**脱离持有集谈卡的价值是范畴错误**。
- **每万菲林 = Δ(c) / (成本/10000)**，只作诊断，且分母必须是**实际增量成本**（见 §2.2b），
  不是该卡满配的总成本。

### 3.3 ★ 完全下位：价值严格为 0

这是本文最重要的一条，也是容易被"有成本就该有价值"的直觉带偏的一条。

**定义（完全下位 / strictly dominated）。** 给定持有集 S、预算 B、评价窗口与场景集合，
若加入卡 c 后，最优可行收益不变，且 c 也无法解锁任何原本不可行的队伍、房间或评分路径，则

```
Δ(c | S, B) = 0     （严格等于，不是"约等于"或"算不出来"）
```

**为什么这是有效结论而不是失败：**

- 决策含义明确：**在你的账号上，不要为这张卡花菲林**。省下的菲林可用于其他卡或留作实物期权。
- 它符合"不抽永远可行"的结构：当一张卡被现有选择完全覆盖时，它的边际贡献天然是 0。
- 典型情形：新卡在数值、机制、队伍位置三方面都被已持有卡覆盖（同定位、同属性、同房间适配），
  或它只能进入已被更强组合占满的房间。

**必须与另外两种 0 分开报：**

| 情形 | 含义 | 报告方式 |
|---|---|---|
| **确证完全下位** | 加入后最优值不变，且已排除协同/补位/新房间 | 「0（完全下位，建议不抽）」 |
| **未持有未抽** | 最优策略本来就没买它 | 「0」（同显示 0，成因不同） |
| **搜索未发现增益** | 本次 beam 宽度/候选池下没找到增益 | 「0（搜索上限，证据强度：弱）」 |
| **负差被截断** | 禁用重规划反而更高分 ⇒ 说明原策略非最优 | 「搜索不自洽」——是 bug 信号，不是卡的属性 |

最后一种尤其危险：`computeCardValuesVcg` 里 `Math.max(0, base − counter)` 会把"禁用它反而更好"
直接显示成 0，读者会把它误读成第一种。**负差是搜索质量的告警，不是价值结论。**

> **已落地**（2026-09-29）：`CardValueVcg` 新增 `rawGap`（未截断原始差）与 `searchInconsistent`
> （`rawGap < 0`）；`value` 仍是展示口径（下界 0），`rawGap` 是自洽性证据。页面给不自洽行打 ⚠ 并降调，
> hover 提示"加大 beam 宽度重算"。测试用两期合成 oracle 钉住：窄 beam（1）下 `rawGap = -40000`
> 且标不自洽；放宽到 8 后同一问题总分从 10000 升到 50000——证明负差来自搜索近似，不是卡的属性。
> 对照用例钉住"真·完全下位"：`value 0` 且 `rawGap` 恰为 0、不标不自洽。

### 3.4 历史已兑现 ≠ 未来增量

- **过去**：卡在它首次 UP 之后的每个期，若实际贡献过分数，那段历史价值是**已实现**的，
  不因后来出现上位替代而被追溯抹去（Chart 5 的"累计兑现"就是这个口径）。
- **未来**：若今天已持有上位替代，那么**补抽这张下位卡的未来增量可以是 0**。
- 两者不矛盾：一个是已发生的事实，一个是面向未来的边际。价值报告必须写清是哪一个。

## 4. 常见误用（思想层面）

1. **用 ROI 排序卡**。菲林是共享预算，A 的 ROI 高不代表该先抽 A——
   可能 A 便宜但提升小，B 贵但能解锁一整支队伍。正确问法是"同等预算下哪个行动更优"。
2. **把平均当边际**。累计/期数（场均）用于**跨实装时点可比**，是好读数；
   但决策看边际。当前 `recentAvg` 实际是"末 3 个房间"而非"近 3 期"——多房间的期会超采样。
3. **把"无观测"记成 0**。"未出场/无配对"计 0，混淆了「确实没兑现」与「没有数据」。
   前者是结论，后者是缺失。二者在统计上必须可区分（至少要有计数与置信提示）。
4. **忽略机会成本**。沉没成本（已抽到的卡）不参与未来决策；但**预算的机会成本必须参与**：
   花掉的 15000 就是放弃了另一张卡的 15000。
5. **假设价值可加**。留一价值不可加总：互补的两张卡（A+B 才成体系）各自被禁都掉大分，
   但两者之和会远超"同时禁两张"的损失。逐卡台账是**边际外部性**，不是可分配的份额。
6. **把归档差分当因果**。同作者配对吸收了玩家技术与房间难度，但没控制配装、队友、选稿偏好与尝试次数；
   它是**描述性**的（treatment-on-the-treated），不是"抽了这张卡就提升 X 分"。
7. **分数口径混用**。归档单房 65000 = 伤害分 60000 + 操作分 5000；
   不能统一减 5000 当作引擎伤害分——操作分不是人人拿满。
8. **用随机模拟替代期望**。已被裁决删除，不要再引入保底状态机或分位数把握度。

## 5. 建议的方向（思想层面）

1. **主目标改为固定期限累计分数最大化**（r = 0），每万菲林降级为诊断列。
2. **价值一律带"相对哪个持有集"**：输出 `Δ(c | S)`，并显式标注 S（新号 / 成型号 / 自定义）。
3. **零价值三态化**：确证完全下位 / 搜索未发现 / 搜索不自洽，三者在 UI 与数据上分开。
   其中"搜索不自洽"应作为搜索质量指标暴露（例如报出 rawGap < 0 的次数），而不是被截断吞掉。
4. **成本按实际增量档位计**：升级路径上分母用增量成本，不用满配总成本。
5. **角色与音擎分开定价、分开持有**：M0–M6 与 R1–R5 是两条独立阶梯，
   不必强制"先专武再满配"的串联结构（现有 `nextPurchase` 要求 tier2 之后才能到 tier3）。
6. **三根时轴解耦**：收入按版本日历发放、购买受首 UP 窗口约束、结算按期进行；
   收入不应因某期 Boss 少而缩水。
7. **历史与未来分开呈现**：Chart 5 的累计兑现是已实现历史；规划器输出的是未来增量。
   同一张卡可以"历史很高、未来为 0"，这需要被清楚地讲出来，而不是取平均。

## 6. 边界与未决

- **归档只作单条部署对照，不作误差判据**（用户裁决 2026-09，见 `AGENTS.md` §3）：
  归档是 approved 顶尖投稿，存在幸存者偏差，配装/操作/词条未知，不据此校准引擎。
- **规划器的已知偏差**：`maxIter` 未收敛队被排除（青衣系整类），模型偏好与真实 meta 有差距
  （见 `docs/FEATURES_GUIDE.md` §4.2/§4.5）。完全下位的判定因此是"在当前模型内"的判定。
- **复刻不建模**：首 UP 窗口为唯一购买窗口（现有口径）。这意味着"等复刻"不被当作可用策略，
  从而可能**高估**首 UP 的紧迫性。
- **成本常量的核验边界**：15000 / 10000 是项目内的期望基准（源自游戏内调频详情公示的综合出率），
  本文未独立复核官方精确数值；它们是**约定**，改动需同步 `filmEconomy.ts` 与相关文档。
- **待用户裁决**：是否要把"完全下位"作为一个显式的输出标签（而非让读者自己从 0 里读出来）。
