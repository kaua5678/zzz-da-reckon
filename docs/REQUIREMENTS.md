  - `AnalyzeCinemaUpliftParams` 目前只注入 `readDamage` / `readUltimateTotal` 两个读取器。

**要做的事**

1. 逐级命座（1→6 命）除了**伤害**，再给出**失衡、积蓄、喧响、能量**的增量 / 提升率，

2. 用户说的是「等」，即**同类可量化指标都应纳入**。你自行判断还有哪些该进
   （例如异常 / 紊乱相关、连携次数、支援点数…）。进得了的就进；进不了的写明为什么进不了。
3. 新增栏位必须和伤害栏**同场景、同固定条件**逐级对比（除下面「必须注意」里那条例外）。

**⚠️ 必须注意：这条需求和现有口径有冲突，你得自己定方案**

`cinemaUplift.ts` 顶部口径写着：命座提升率用 `enemy.stunCountLock` **把失衡次数锁死**再逐级对比，
因为 3/5 命的技能等级会抬失衡值 → 失衡次数↑ → 连携/喧响↑ → 失衡总量自激、阈值无稳定点。

⇒ **「失衡」这一栏如果直接在"锁死失衡次数"的场景里算，很可能恒为 0 或极小。**
这是口径冲突，**不是 bug**。需要你自己选一个方案，例如：

- **方案 A**：失衡栏**另开一组对比**（不锁 `stunCountLock`，同一收敛规则各算各的），
  并在页面上明确标注「失衡栏不锁次数、与伤害栏口径不同」；或
- **方案 B**：改用不受次数锁定影响的量作为指标，
  例如「单次失衡值」「失衡值累积速率」。

两种都可以。**选一个 + 写清依据 + 标注回退点**，不要留成模糊状态。

**验收**

- 新增指标在**每一级命座**都有数（不能只出第一级）。
- 保留现有自检三态语义不变：`ok` / `execLevel` / `unimplemented`；
  `changedFields` 的口径不要退化。
- `__tests__/cinemaUplift.test.ts` 与 `allAgentsSweep.test.ts` 里的既有不变量**必须继续绿**；
  新增指标要有对应测试（至少覆盖「新增栏位不是恒 0」）。
- 页面列名用中文、与游戏内叫法一致（失衡 / 积蓄 / 喧响 / 能量）。

## R2 · 开发流程提速：**先量，再改**

1. **先测量，别先优化。** 从你自己的运行记录里统计「一张卡的时间都花在哪」：
   读代码 / 写改动 / 跑验证 / 写文档 / 提交 / 等待。给出**真实数字**（可以抽样最近 10~20 张卡）。

## 问题的精确形式（已由实测钉住，**这是开工的地基**）

本仓已有**精确**恒等式（`@fact engine:失衡易伤/信用恒等式`，锚 `stunVulnSummary.ts#computeStunVulnSummary`）：

```
credit ≡ [always × D_直伤 + (fullCredit − always) × Σ_直伤(伤害 × cov)] / D_全池
   always = 面板 stunDmgMultiplierBonusAlways（经 Cap 钳后 /100）
   cov    = 行级 stunCoverage（轴模式 = 1/0 两档；异常行恒按 1）
```

**实测误差 ≤ 7.8e-16**（`.zc/perf/T184identity.perf.ts`，4 队 × 锁 2~5）。

⚠ **简化式「credit = 轴内伤害占比 × fullCredit」只在 `always = 0` 时成立**：
首版 @fact（2026-10-16 上午）把它写成了无条件恒等式，**同日下午被 T184 代理的 980 格普查证伪**——
`always ≠ 0` 的队（**全库含扳机 1361 的 4 支 = 有轴队的 11%**，always=35）偏差最大 **0.198**。
根因：`calcStunMultiplier` 是 `alwaysMult + (fullMult − alwaysMult) × cov` 的**线性插值**，
always 通道**全时段生效、轴内外都吃**，所以它不从「轴内占比」里来。
⇒ **`coverageRate`（页面「兑现率」）不等于轴内伤害占比**（有 always 通道时被抬高），
用到它做推断时必须先扣 always。

而**无轴**时引擎按时间均匀给易伤：`时间覆盖率 = min(1, 失衡次数 × 单窗 / (battleTime − invincibleTime))`。

⇒ 所以用户说的「未知易伤贡献」= **两个因子的乘积**：

```
轴模式易伤贡献 = 时间覆盖率 × 集中度倍数
                   ↑ 可解析算         ↑ 用户要的「未知量」
```

**实测样例**（般岳+琉音+卢西娅，单窗 12s / 预算 180s）：

| 失衡次数 | 时间覆盖率 | 有轴 兑现率 | 无轴 兑现率 | 集中度倍数（有轴） | 集中度倍数（无轴） |
|---:|---:|---:|---:|---:|---:|
| 1 | 10.0% | 36.5% | 9.7% | 3.65× | 0.97× |
| 2 | 20.0% | 59.5% | 19.4% | 2.98× | 0.97× |
| 3 | 30.0% | 60.0% | 29.1% | 2.00× | 0.97× |
| 4 | 40.0% | 62.7% | 38.7% | **1.57×** | 0.97× |
| 5 | 50.0% | 62.3% | 48.4% | 1.25× | 0.97× |
| 6 | 60.0% | 62.2% | 58.1% | 1.04× | 0.97× |
| 8 | 80.0% | 84.3% | 77.6% | 1.05× | 0.97× |

**读法（这三条就是算法要解释的东西）**：
1. **无轴的集中度恒 ≈ 0.97×**（引擎把易伤按时间均匀摊到全池，几乎不集中）——所以「无轴偏低」是**结构性**的，不是数值误差；
2. **有轴的集中度随失衡次数单调衰减**（3.65× → 1.04×）：次数越多，失衡时间占比越高，能「集中」的余量越小；
3. **有轴的兑现率在 3~6 次之间几乎饱和在 62%**（不是线性）——因为轴内伤害总量有天花板（轴只盖得住那么多招），
   再多失衡次数只增加轴外伤害。**这条天花板才是「自动模拟」要估的核心量**。

## 要做的事（三步，每步都要机器判据）

1. **量化「手动轴集中度」**：对全部有轴预设 × 全部（队 × Boss × 失衡次数）组合，实测
   `集中度倍数 = 有轴兑现率 / 时间覆盖率`，产出**它的决定因素**（候选：轴内动作的总倍率 / 轴内时长 / 队伍总倍率分布 / 失衡窗口数）。
   判据：**拟合出的代理量与实测集中度的相关性**（要给出 R² 或逐队残差分布，不是「看起来像」）。
2. **给无轴/无预设的队伍估「等效集中度」**：用户要的「自动模拟易伤」。

**集中度倍数随失衡次数强衰减**（按 lock 聚合中位，有轴臂）：

```
lock:      1      2      3      4      5      6      8
conc:    2.802  2.460  2.083  1.825  1.454  1.247  0.967
线性拟合: conc ≈ 2.955 − 0.271×N   R² = 0.969
倒数模型: conc = 1.124 + 1.929/N   R² = 0.791（不如线性）
conc×lock: 2.80 / 4.92 / 6.25 / 7.30 / 7.27 / 7.48 / 7.73（lock≥4 后趋稳 ≈7.3~7.7）
```

物理含义：**N≤3 时手动轴集中度优势最大（1.8~2.8×），N≥6 后基本消失（≈1.0×）**——窗数一多，
窗口总时长本身就把战斗时间占满（lock8 的时间覆盖率已达 82%），没有「集中」的余地。

**稳定性**（决定性判据）：同队跨 N 的 CV = 0.25~0.65（**CV<0.10 的队 = 0/35**）；同 N 跨队 CV 0.14~0.38。
⇒ 既不能当成队无关常数，也不能当成次数无关常数 ⇒ **要精准就必须逐档实测**（或至少带 N 依赖项）。

**对算法设计的约束**：任何「自动模拟易伤」的候选路线（(a) 倍率排序代理 / (b) 通用轴 / (c) 经验公式）
**必须显式带 N（失衡次数）依赖**，且验收判据是**逐档误差**（不是「整体看起来对」）。

## 缺口（已量化，见 `axis-vuln-uplift-reference.md` §十二）

当前无轴模型：`stunCoverage = min(1, 失衡次数×单窗/有效时长)` ⇒ **全池每招同比例**吃易伤。
实测「直伤行实打覆盖」与 `stunCoverage` **逐位相等**（差 ≤0.005）⇒ 确实假设了**完全均匀**。

而真实玩家（即使不捏轴）会把高倍率招留到失衡窗 ⇒ 实际集中度 ≈ **1.8×**（手动轴中位）。
⇒ **无轴模型把真实玩家的 ~1.8× 当成了 1.0×** —— 这就是「不真实」的确切含义。

## 要做什么（**不生成轴**）

在**无轴的易伤覆盖率**上乘一个**估算的集中度**：

```
无轴有效覆盖率 = 时间覆盖率 × conc_est(N) × k
                  ↑ 引擎既有（时间覆盖率）  ↑ 数据驱动估算   ↑ 用户系数（默认 1.0）
现在：conc_est 恒为 1.000、k 不存在 ⇒ 无轴 = 完全均匀摊
```

**用户 2026-10-17 裁决：「最好可以调整，因为这种很难确定」** ⇒ 必须是**可调滑块 + 可关开关**，
不是写死的倍数。`k` 默认 1.0（= 数据驱动估算）；**关掉开关 ⇒ 回到旧口径（逐位相同）**。
详见 `axis-vuln-uplift-reference.md` §12.4（含 UI 的游戏场景措辞 + 5 条判据）。

`conc_est(N)` 的来源 = `§10.4` 已达标的路线（通用轴估算，逐档中位误差 **8.1%**、留队 **7.2%**），
**但它不生成真轴、不注入轴路径**——只是一次估算，把标量乘进覆盖率。

## 硬约束

1. **不污染轴模式**：轴模式覆盖率仍是 1/0 两档（§十二 12.3 纪律 1）；
2. **必须可关 + 来源可见**：用户能看到「无轴现在是估算的」，并能一键回到 `conc_est = 1`（旧口径）；
3. **N 依赖**：`conc` 随失衡次数强衰减（N=1 时 2.8×、N=8 时 1.0×），**不许用常数**；
4. **判据 = 逐档误差**（以手动轴为靶子，中位 ≤10%），不是「整体看起来对」；
5. 时间/物化行口径不动（只改易伤覆盖率的标量）⇒ `timeGolden`/`timeFillRatchet` 预期**零 delta**，
   若不为零必须逐条归因（规则 10）。
