## R1 · 命座提升率：除伤害外，再算失衡 / 积蓄 / 喧响 / 能量

**用户原话**

> 命座提升率那里只算了伤害，再加几个栏，算失衡、积蓄、喧响、能量等

**现状（已定位，供你少走弯路）**

- UI：`src/views/ResourceUtilizationPage.vue:199`
  （表头文案：「命座提升率（当前配队与滑块下，逐级影画带来的伤害增量）」）
- 算法：`src/composables/cinemaUplift.ts`
  - `CinemaUpliftEntry` 目前**只有一个收益指标** `gainPct`（伤害提升%）；
    另外三个字段 `ultBefore` / `ultAfter` / `changedFields` 是自检用，不是收益栏。
  - `AnalyzeCinemaUpliftParams` 目前只注入 `readDamage` / `readUltimateTotal` 两个读取器。

**要做的事**

1. 逐级命座（1→6 命）除了**伤害**，再给出**失衡、积蓄、喧响、能量**的增量 / 提升率，
   并在页面的命座提升率表里**各占一栏**（用户原话：「再加几个栏」）。
2. 用户说的是「等」，即**同类可量化指标都应纳入**。你自行判断还有哪些该进
   （例如异常 / 紊乱相关、连携次数、支援点数…）。进得了的就进；进不了的写明为什么进不了。
3. 新增栏位必须和伤害栏**同场景、同固定条件**逐级对比（除下面「必须注意」里那条例外）。

**⚠️ 必须注意：这条需求和现有口径有冲突，你得自己定方案**

`cinemaUplift.ts` 顶部口径写着：命座提升率用 `enemy.stunCountLock` **把失衡次数锁死**再逐级对比，
因为 3/5 命的技能等级会抬失衡值 → 失衡次数↑ → 连携/喧响↑ → 失衡总量自激、阈值无稳定点。

⇒ **「失衡」这一栏如果直接在"锁死失衡次数"的场景里算，很可能恒为 0 或极小。**
这是口径冲突，**不是 bug**。需要你自己选一个方案，例如：

- **方案 A**：失衡栏**另开一组对比**（不锁 `stunCountLock`，同一收敛规则各算各的），
  并在页面上明确标注「失衡栏不锁次数、与伤害栏口径不同」；或
- **方案 B**：改用不受次数锁定影响的量作为指标，
  例如「单次失衡值」「失衡值累积速率」。

两种都可以。**选一个 + 写清依据 + 标注回退点**，不要留成模糊状态。

**验收**

- 新增指标在**每一级命座**都有数（不能只出第一级）。
- 保留现有自检三态语义不变：`ok` / `execLevel` / `unimplemented`；
  `changedFields` 的口径不要退化。
- `__tests__/cinemaUplift.test.ts` 与 `allAgentsSweep.test.ts` 里的既有不变量**必须继续绿**；
  新增指标要有对应测试（至少覆盖「新增栏位不是恒 0」）。
- 页面列名用中文、与游戏内叫法一致（失衡 / 积蓄 / 喧响 / 能量）。

**我怎么理解这条需求 / 选了哪个口径 / 依据 / 回退点**（完整证据与探针实测表见 `docs/mcp-cinema-uplift-multi-metric.md`）：

- **加了哪些栏**：用户点名的 4 个（失衡值 / 积蓄 / 喧响 / 能量）+ 从「等」里自行判断纳入的 3 个（强特次数 / 异常触发 / 异常覆盖），共 7 栏；列名用中文、与游戏内叫法一致。
- **哪些没进栏、为什么**（需求第 2 条要求「进不了的写明为什么」）：`chainTotal`（连携）与 `disorder`（紊乱）—— 3 队实测只有雅队会动，其余配队下是恒 `—` 的死列，进栏只增噪声；`derivedEnergy` —— 实测恒等于 `energyTotal`，冗余；`stunCount`（失衡次数）—— 见下条口径决策。日后若用户点名要，`CINEMA_METRICS` 加一项即可，**页面列由该数组派生、不用改模板**。
- **口径冲突：选方案 B**。失衡栏用 `totalStunBuildUp`（失衡值总量），不用 `stunCount`（失衡次数）。依据不是推理而是**引擎探针实测**：3 队 × 命座 0..6 在锁定场景下，`stunCount` 有 2 队恒 Δ0（被 `stunCountLock` 锁死）、只有雅队会动 ⇒ 进栏即死列；`totalStunBuildUp` 三队全部会动（−4354.6 / +1486.2 / +1768.2）。锁固定的是「次数」，本栏量的是「总量」，两者**正交** ⇒ 锁下仍有信息，且不违背原口径立锁的意图（防失衡总量自激、阈值无稳定点）。
- **方案 A 为什么否决**（技术可行但不选）：探针顺带量了锁的量级影响 —— 同号、差 2~3×（般岳队锁内 +1486.2 / 锁外 +766.2；仪玄队 −4354.6 / −1572.1）。A 需让每级影画多跑一遍完整场景（本已是最慢的分析之一）⇒ 耗时翻倍；且同表会出现「同一指标两种口径」两列，读者必须先理解锁的作用才看得懂。否决理由是**成本与可解释性**，不是 A 错；若日后明确要「不锁口径」，实现路径见上述文档 §7 下一步 2。
- **顺带做的一处口径变更（需知情，可逆）**：`ultBefore` / `ultAfter`（大招次数）原先在锁外单独读，现改为与伤害及新指标**同在锁定场景内读**，使同一行数据同源（否则一行里混两个口径）。**回退点**：`src/composables/cinemaUplift.ts` 的 `readScene()` 里把 `ult` 那一行移回锁外单独读即可（一处改动）；测试「同一场景纪律」会红 ⇒ 红即证明改到了（负控 M2 已验证过）。
- **另一处自决**：伤害栏的 `+0%`（实测 4→5 命出现）**故意保留**，没统一成新栏的 `—`。它是改动前的既有行为，且正是「该命座无可测伤害」的信号载体（配合自检角标 ⚠无变化）；统一成 `—` 会削弱死亡数据的可见性。新栏则采用「按本栏显示位数四舍五入为 0 ⇒ 显示 `—` 且不着色」，理由是实机 DOM 读回抓到两个截图看不出的缺陷：`异常覆盖` 每行印 `+0pp`（rate 分支抢在零变化判断之前）、`-18.2 -0%`（Δ/基数 = −0.04% 的纯噪声）；精确值不丢，仍在单元格悬浮提示里（before → after 全精度）。
