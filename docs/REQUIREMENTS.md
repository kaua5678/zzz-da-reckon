  - `AnalyzeCinemaUpliftParams` 目前只注入 `readDamage` / `readUltimateTotal` 两个读取器。

**要做的事**

1. 逐级命座（1→6 命）除了**伤害**，再给出**失衡、积蓄、喧响、能量**的增量 / 提升率，
   并在页面的命座提升率表里**各占一栏**（用户原话：「再加几个栏」）。
2. 用户说的是「等」，即**同类可量化指标都应纳入**。你自行判断还有哪些该进

3. 新增栏位必须和伤害栏**同场景、同固定条件**逐级对比（除下面「必须注意」里那条例外）。

**⚠️ 必须注意：这条需求和现有口径有冲突，你得自己定方案**

`cinemaUplift.ts` 顶部口径写着：命座提升率用 `enemy.stunCountLock` **把失衡次数锁死**再逐级对比，
因为 3/5 命的技能等级会抬失衡值 → 失衡次数↑ → 连携/喧响↑ → 失衡总量自激、阈值无稳定点。

⇒ **「失衡」这一栏如果直接在"锁死失衡次数"的场景里算，很可能恒为 0 或极小。**
这是口径冲突，**不是 bug**。需要你自己选一个方案，例如：

- **方案 A**：失衡栏**另开一组对比**（不锁 `stunCountLock`，同一收敛规则各算各的），
  并在页面上明确标注「失衡栏不锁次数、与伤害栏口径不同」；或
- **方案 B**：改用不受次数锁定影响的量作为指标，
  例如「单次失衡值」「失衡值累积速率」。

两种都可以。**选一个 + 写清依据 + 标注回退点**，不要留成模糊状态。

**验收**

- 新增指标在**每一级命座**都有数（不能只出第一级）。
- 保留现有自检三态语义不变：`ok` / `execLevel` / `unimplemented`；
  `changedFields` 的口径不要退化。
- `__tests__/cinemaUplift.test.ts` 与 `allAgentsSweep.test.ts` 里的既有不变量**必须继续绿**；
  新增指标要有对应测试（至少覆盖「新增栏位不是恒 0」）。
- 页面列名用中文、与游戏内叫法一致（失衡 / 积蓄 / 喧响 / 能量）。

## R2 · 开发流程提速：**先量，再改**

**用户原话**

> 我们这个是不是收尾都要跑一次测试，会不会大大延长开发时间。让 opus 优化一下开发流程吧，感觉有点慢了。**如果是必要的那就算了。**

**要做的事（顺序不能反）**

1. **先测量，别先优化。** 从你自己的运行记录里统计「一张卡的时间都花在哪」：
   读代码 / 写改动 / 跑验证 / 写文档 / 提交 / 等待。给出**真实数字**（可以抽样最近 10~20 张卡）。
2. 基于数字判断：**验证到底占多少**？是不是主要瓶颈？如果不是，就直说，别硬改。
3. 如果验证确实是瓶颈，再找**不降低保证强度**的优化。可以探索（但不限于）：
   - **验证分层**：纯改名/纯搬迁卡 vs 触及计算路径的卡，是否真的都需要全量零差？
     （注意：这个判断本身要有依据，不能靠"看起来安全"）
   - **增量/子集**：全量 dump 的场景集能否只跑「受影响的那部分」？影响面怎么算才可靠？
   - **并行**：验证与文档/派单/下一张卡的设计能否重叠？
   - **工人在等什么**：`vue-tsc -b` 之类的固定开销有没有办法摊薄（增量编译、缓存）？
4. 把改后的流程写进 `docs/mcp-worker-task-queue.md`（或专门的流程文档），并说明**为什么这样是安全的**。

**硬约束**

- **不得以降级验证强度换速度。** 任何会削弱「逐位零差」保证的改动，
  必须**单独列出来**并写明「这会让什么类型的错误漏过去」，让用户裁决，**不要自己拍**。
- 改动前后都要能跑通，且给出**可对比的数字**（改前 X 分钟/卡 → 改后 Y 分钟/卡）。
- 若结论是「现有流程已经接近必要下限」，**直接写这个结论并说明依据**，这也是合格答案。
