## §0 一句话结论

**用户的前提「合轴达到上限也包容不完」在全库当前数据下只对 `auto-1431-1481-1491` 一队成立（97 队里 1 支），
而且它确实是「容量真的不够」——不是算法算错。**

具体读数：该队 `Σ容量 = 30.79s` 而溢出 `= 40.85s` ⇒ **容量比溢出少 10.06s**，
所以 `take = 29.68s` 之后**必然**剩 `11.17s` 没处去，最终被装配期截断成 `cut = 12.56s`。
**⇒ 「提高 40% 上限」在数字上确实能解决它**（r=0.6 即 `cut = 0`），但**该档位已被用户 2026-10-05 裁决维持 0.4**，
本稿不重提、只如实列出后果。

**本稿另有一个独立发现（与上面的结论不冲突、但值得单独修）**：
吸收子问题的迭代上限写死 8 轮，而该队的**不动点需要 8 轮以上**（第 8 轮仍在以 ~1e-6 量级移动）
⇒ 源码注释「**实测 ≤5 轮到 1e-9**」在 `9eb11196` 上**已不成立**。
**但它的代价可以忽略**（打满上限与真收敛的 `take` 只差 **7.97e-8s**，`cut` 与伤害**逐位相同**）
⇒ 这是**「声称收敛、实际未收敛」的读数诚实性问题**，**不是截断的成因**。
它的真实价值是**关掉一个假改善入口**：把上限调小会让 `take` 系统性偏大（8 轮 29.681 → 1 轮 30.786）、
`cut` 假性变好（12.56 → 11.02），即**用违反容量约束换取好看的截断读数**（§1.6、§6.2）。

### 1.2 ★ 关键方法：如何把「生产落点那次调用」从 N 次求值里挑出来

`calcTeamResources` 一次预设求值要跑**几十到几千次**（外层不动点轮 + 非轴对照 + 降配二分 6×2 + 下游重算；

本设计稿用的对接键（**97/97 队精确命中**）：

```

```

选它而不是 `timeFeasibleScale` 的原因（实测教训）：多个不同调用可以算出**同一个 scale**，但只有生产落点那次的

**该键的唯一性已被复核**（`recheck.perf.ts` 测试①，主队）：一次求值内 `matched` 可达 20~48 条，

⇒ 命中集内**不存在分歧**，取任意一条（本稿取最后一条）读数相同。**这是本方法成立的关键前提，已单独验过。**

## §3 候选算法对比（步骤 2 核心交付）

### 3.0 先把问题写成数学形式（这是后面所有方案的共同地基）

记（全部在 `iterate` 单轮内，`r` = `comboAlignAbsorbRatio`，`B` = `budget`）：

```
net_i   ≥ 0   槽 i 的净必要前台（= 原始必要 − 静合轴抵扣）
op      = argmax_i net_i                     （操作角色，按定义不可被吸收）
T       = Σ_{i≠op} net_i                     （可吸收总量）
S       = Σ_i net_i                          （团队净需求，> B）
溢出 Δ  = S − B
决策变量 d_i ≥ 0，Σ d_i = take（吸收量）
```

现状的两条**硬约束**（`helpers.ts:394-398` 的注释推导）：

```
(P1) 容量上限（终态口径）：d_i ≤ r·[(net_i − d_i)·s + d_i]，  s = B / (S − take)
(P2) 均摊（按容量比例）：  d_i = (net_i / T) · take            ← 现状用的是这条，不是 LP 解
```

(P1) 在 `Σd_i = take` 处可**整体反解**（这是本稿推导的关键一步）：

```
记 g(s) = r·s / (1 − r + r·s)。(P1) 逐槽求和 ⇒ take ≤ g(s)·T。
现状代码取 take = min(Δ, g·T) 并把 take 按容量比例摊到各槽 ⇒
  · take < Δ  ⟺  Σd_i 被 (P1) 与 (P2) 联立卡住 ⟺ g·T < Δ ⟺ s < 1（封顶激活）
  · take = Δ  ⟺  容量没用完（溢出被吃干净）
⇒ ★「容量用尽」的精确判据 = s < 1（不需要额外读内部量，但从结果对象读不到 s，见 §1.2 的对接方法）。
```

`s` 与 `g` 的自洽条件（把 `s = B/(S − take)`、`take = g·T` 代入）：

```
g = r·s / (1 − r + r·s)
⇒ ★ 不动点方程： T(1−r)·g²  −  [(1−r)S + rB]·g  +  rB  =  0        … (★)
```

**(★) 是二次方程 ⇒ 有闭式解。** 这是本稿对「用户点名运筹学」的正面回答的第一步：

```
情形 1（容量不咬合）：Δ ≤ r·T      ⇒  take = Δ, s = 1（一轮到位）
情形 2（容量咬合）  ：Δ > r·T      ⇒  g* = ( [(1−r)S + rB] − √( [(1−r)S + rB]² − 4T(1−r)rB ) ) / (2T(1−r))
                                    take = g*·T,  s = B/(S − take)
```

> **来源 vs 推导（按任务书调研纪律分开）**
> - **推导**：(★) 是从本仓 `helpers.ts:394-411` 的代码与注释**自己推**的（把两行注释里的约束与迭代式联立消元），
>   不是从文献抄的。**验证 = 数值**：`/home/kaua/t117-scratch/quad2.mjs` 用生产真值 (S=220.847, B=180, T=76.965)
>   扫 r ∈ [0.01, 1] 共 100 档，`max|迭代(200轮) − 闭式| = 8.4e-8`（单精度量级，非算法差）；
>   全库对拍见 §3.4 候选 A。**没有引用任何外部文献来支撑 (★)**。
> - **来源（一般性方法，供定位用）**：这类「按比例分摊 + 每个分量各有上限 + 总量守恒」的问题，
>   运筹学里属于**带上界的连续资源分配 / water-filling**族；其「填满最便宜的一档、把它钉住、
>   剩下的重新分摊」的求解范式在通信网络里叫 **progressive filling**，与 **max-min fairness** 等价
>   （来源：[Bertsekas & Gallager《Data Networks》的 progressive filling 算法](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2011/EECS-2011-18.pdf#5#3)
>   明确写「progressive filling method implements the algorithm in [Bertsekas1992DataN], which should guarantee
>   max-min fairness」，该段同时说明「边逐个饱和、经过饱和边的路径停止增加」；
>   逐字核对过的段落见 [此 PDF 的第 5 页第 3 片段](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2011/EECS-2011-18.pdf)。
>   **⚠ 但我没有把它作为本仓方案的依据**——本仓的 (P1) 是「比例 × 封顶后终态」而非「绝对上界」，
>   两者的解不是同一个，见 §3.5 的反例。这一点**必须由本仓数据定，不能靠类比**。）

### 3.1 候选 A：**闭式解**（把 8 轮小迭代换成二次方程求根）

| 维度 | 内容 |
|---|---|
| **数学形式** | 一元二次求根 + 一枝剪枝。**不是** LP、**不是**迭代法；是**不动点方程的解析解**。 |
| **满足用户模型哪几条** | ① 四步序不变（只替换第三步**内部**的求解器，接口 `take`/`dyn[]` 逐位同语义）；② **唯一不动点**（二次方程在 `take < Δ` 分支上取**较小根**，且该根在 `(0, Δ/T)` 内 ⇒ 唯一）；③ **迭代有限可停**——**迭代次数 = 1**（现状是 ≤8 且可能不收敛）。 |
| **可证伪的预测** | ① **严格对拍（34 支闸门队 × r∈{0.1,0.3,0.4,0.7,1}）**：`max\|Δcut\| = 0`（逐位）；`max\|Δdyn\| ≤ 8.04e-8`（浮点量级）；`max\|Δdmg\| ≤ 7.7e-9 %`。**已实测**，见 §3.4。② 主队 r=0.4：`take` 差 7.97e-8s（**必须写进提交说明，不许当成 0**）。③ **算力**：34 支闸门队的迭代总轮数 `41 → 1`（r=0.4）；单预设 `auto-1431-1481-1491` 进闸门 2701 次 ⇒ 省 7×2701 ≈ **1.9 万次浮点迭代**。 |
| **代价** | 改动面**极小**：`helpers.ts:402-415` 那段 `for (let it = 0; it < 8; it++)` 换成求根（~12 行）。**不动** `assembleSlot` 整数装包、**不动** `feasibleScale`、**不动**任何基线。风险 = 判别式在极端参数下可能为负（须保留情形 1 的一轮分支）。 |
| **失败模式** | ① `disc < 0` ⇒ 退化成现状迭代（保留兜底）；② `T ≈ 0`（单角色 / 队友净必要全 0）⇒ 现状已有 `teammateTotal > 1e-9` 闸门，照留；③ **非单调性**（`take` 随 r 单调 ↑ 的性质）：闭式解在 `take = Δ` 与 `take = g*T` 两枝的交界处**连续但可能不光滑** ⇒ 必须保留「`Δ ≤ r·T` 走情形 1」的显式分支，否则交界处会跳变。 |

> **诚实标注**：候选 A **不解决任何截断**（主队 cut 仍是 12.557s，**因为容量确实不够**，见 §0/§2）。
> 它的价值是**把「声称收敛」变成「真的收敛」**（关掉 §1.6③ 的假改善入口）。
> **如果目标只是「消截断」，A 不是答案**——消截断要靠 r（已裁决不做）或候选 C（波及 18/97 队）。
> ⇒ **A 是一条「低风险、零 delta 的读数诚实性修复」，不是「解决用户问题」的方案。**
> 它值得做，但**不要把它当成对「包容不完怎么办」的回答**——那个问题的答案是 §4B/§4C 的三条路。

### 3.2 候选 B：**上限解耦**（容量按「吸收前净必要」取，而非封顶后终态）

| 维度 | 内容 |
|---|---|
| **数学形式** | 把 (P1) 的右端从 `r·[(net_i−d_i)·s + d_i]` 改成 `r·net_i` ⇒ **上限不再是 d 的函数** ⇒ 整个问题退化为 **`take = min(Δ, r·T)` 一轮到位**（无需迭代，无耦合）。 |
| **满足用户模型哪几条** | ① 四步序不变；② 唯一不动点（退化为一轮，**平凡唯一**）；③ 迭代有限可停 = 1 轮。**但它牺牲了「吸收与封顶耦合」这条本仓既有口径**——现状注释明确说按吸收前取 40% 会让队友终态里被判并行的份额**远超 40%**（实测 1481 终态 67.8s 里 57.1s = 84%）。 |
| **可证伪的预测** | 主队 r=0.4：`Σdyn 29.681 → 30.786`（+1.105）、`scale 0.94159 → 0.94706`、`cut 12.557 → 11.024`（**−1.53s**）、伤害 `111.318M → 113.874M`（**+2.30%**）。**全库变动队 = 1**（只有主队）。 |
| **代价** | 同样只改 `helpers.ts` 一小段（删掉迭代）。**代价是语义**：破坏「终态被并行份额 ≤ 40%」这条**已实测钉过**的口径（注释里有 `1481 终态 67.8s 里 57.1s` 的读数）⇒ 等于**把用户裁决的 40% 上限换了个测量基准**，属于**改政策口径**，不是改算法。 |
| **失败模式** | ① **它会让「40%」不再可解释**（用户 2026-10-05 裁决是「初始默认 40% 就按 40 来算」，没说按哪个 40%）；② 极端下 `r·T > Δ` 仍走情形 1，无新风险；③ **收益 +2.30% 有诱惑力但只对 1 队**——为 1 队改掉一条已被实测锁定的口径，性价比与可解释性都差。 |

> **本稿立场**：候选 B **不是**推荐项，列出它是为了让「40% 该按什么取」这个**已被裁决过的量**不被悄悄换基准。

### 3.5 ★ 为什么「water-filling / max-min」在本仓**不是**直接可用的类比（反面结论，来自推导）

任务书要求正面回答「这属于哪类问题」。我推导后的结论是：

**本仓的问题不是标准的 max-min / water-filling 问题**，理由是 (P1) 与标准形式**结构不同**：

```
标准 water-filling：  d_i ≤ c_i（固定上界）        ⇒ 解 = 填到某水位 λ：d_i = min(c_i, λ)，Σd_i = B
本仓 (P1)：           d_i ≤ r·[(net_i − d_i)·s + d_i]（上界**含 d_i 自己**，且 s 依赖 Σd_i）
```

- 标准形式的「填满最便宜的一档再钉住」之所以成立，靠的是**上界 c_i 与 d_i 无关**（钉住后剩余问题同构）。
- 本仓的 (P1) **上界随 d_i 增大而增大**（`d_i` 越大，`(net_i−d_i)·s + d_i` 里被压的部分越少）⇒
  **不是简单的「先填满低容量槽」**，而是**一个整体耦合的标量不动点**（全队共享一个 `s`）。
- ⇒ 这正是「**吸收与封顶不是两个独立旋钮**」（任务书 §2.2）的数学表述：**全局只有 1 个自由度**（`take` 或 `s`），
  槽间分配由容量比例 (P2) **唯一确定**。**没有可优化的槽间分配自由度** ⇒ **LP 在这一层没有决策空间**。
- ⇒ **结论**：把本问题称成「线性规划 / max-min 公平 / water-filling」都属于任务书警告的**名字联想**。
  它的正确定位是：**一元标量不动点问题，且有闭式解**（候选 A）。

> 这也解释了为什么 §3.3 的候选 C 是**唯一真正改变可行域**的方案 ——
> 它改的是「谁是可吸收的槽」（可行域的**维度**），而不是「怎么在给定可行域里分」（那一层没有自由度）。

## §4 三个必答问题（A/B/C）的正面回答

### A. 「占用剩下的时间」这个目标函数怎么写？

**答：在当前动作集合下，这个目标函数是空的（不可达目标），必须如实说。**

实测支撑：
- 34 支闸门队里 **29 支平A池 = 0**；主队 `Σ平A池 = 0.00`、留白 = 1.39s。
- **平A 池是唯一「可自由加」的连续动作**（`timeWeight` 分配、`availableBasicTime` 驱动），
  且**它是唯一不参与截断的动作**（`timeTruncation.ts:53-56,72`：「平A行是填充项，不参与截断」、
  `isTruncatable = isFrontlineExecution(e) && e.moveId !== 'basic_attack'`）。
  ⇒ **「往剩余时间里加动作」在引擎里唯一的合法载体就是平A行，而它有两个硬限制**：
  ① 供给受限（`availableBasicTime = budget − ΣcappedNecessary + relief + refund`，§`helpers.ts:456`）；
  ② 单槽物理上限（`totalTime − totalNecessary`，水填法 `helpers.ts:469-485`）。
  闸门队里 29 支的这个池**已经被削到 0** ⇒ 「先削平A」这一步**已经走到底**。
- 剩下的「时间」在引擎里**没有对应的动作载体**：
  - **不是留白**（留白 = 账本 > 物化行的**欠打**，是缺陷不是手段）；
  - **不是走位/蓄力/换人**——这些在引擎里**没有时长模型**（用户 2026-09-27 已明确否决「引擎补全轴」的路线：
    「高手在失衡期让琉音上场……**隐含的条件是什么，这些你都无法设计**」）。
- ⇒ **「占完剩下的时间」在「平A 削到 0 之后」不可达**。可达到的形式只有两种，**都不是「加动作」**：
  1. **提高吸收比 r**（把更多前台判为并行）——**已被用户 2026-10-05 裁决维持 0.4**，本稿不重提；
  2. **削减必要动作**（= 现状的 `feasibleScale` 封顶 + 整数装包截断）——**这正是用户问的「怎么办」**。

**⇒ 结论（写进设计的口径）**：「占完剩下的时间」应当被重新表述为
**「让净占用 == 预算」**（等式约束），而**不是**「给剩余时间找动作」。
在主队上 `net`（超时判定口径）恒 ≤ 预算（硬不变量，`comboAbsorbBeforeTruncation.test.ts:73` 钉着），
所以这个等式**已经成立**——真正没有被满足的是**「想打的招式都打得上」**，
而那受 `净占用 ≤ 180` 与 `吸收上限 0.4` 两条硬约束支配 ⇒ **只能削减**。

### B. 吸收上限该不该是 0.4？上限用尽后的降级顺序是否合理？

**上限本身：不再问。** 用户 2026-10-05 已裁决「初始默认 40% 就按 40 来算」。
补充**实测**：数据面上 **0.4 → 0.6 是唯一有意义的档位**（§1.7：`Σcut 13.51 → 0.95`，主队 cut 清零）；
0.6 → 0.7 → 1 对**任何一队**都不再改变截断（`Σcut` 恒 0.95，即那支不经过吸收的 `yidhari-norma-lucia`）。

**降级顺序（这是可以问的部分）——现状顺序与实测代价：**

```
① 平A 池削到 0        （34 支闸门队里 29 支已到 0）
② 动态合轴吸收 ≤ r×净必要（34 支里 33 支一轮吃干净；1 支卡在 s<1）
③ feasibleScale 全队等比封顶（全库 97 队里当前激活 = 0 队，见 §1.3）
④ 装配期整数装包截断（cut > 1s = 1 队 / cut > 0.01s = 2 队）
```

**实测评价**：这个顺序**与用户模型一致**（§1 的四步），且**③ 当前是死的**（0 队激活）——
`feasibleScale` 只在「**吸收后**的 Σ净 > 预算」时才激活，而现状 §3.3 显示吸收后 33 支全部 ≤ 预算、
唯一那支落在 ④（截断）。
⇒ **可问的具体点**：`auto-1431-1481-1491` 在 ④ 被砍 12.56s，而它在 ③ 上 `scale = 0.94159`
（**即 ③ 其实激活了**——`scale < 1` 当且仅当 `s < 1`）。
**⚠ 这里有一个本稿发现的、值得用户看一眼的语义问题**：`s`（吸收子问题的切分点）与
`feasibleScale`（封顶比例）在代码里是**同一个量**。逐字核对（`9eb11196`）：

```
helpers.ts:407  const s = remain > budget ? budget / remain : 1      // remain = Σ净 − take = sumAbsorbedNet
helpers.ts:426  const rawScale = !axisMode && sumAbsorbedNet > budget && sumAbsorbedNet > 0
                                 ? budget / sumAbsorbedNet : 1
```

⇒ 除 `axisMode` 闸门外，**`s` 与 `rawScale` 是同一个表达式**；实测主队 `s == scale == 0.941589651`
（`recheck.log` 的 `take|s|scale` 三元组逐位相同）。
**⇒「吸收没吃干净」与「全队等比封顶」在数学上是同一件事的两面。**
所以「上限用尽后先封顶再截断」这句话在实现里**只有一步**，不是两步。**这不是缺陷**（推导见 §3.0 的联立），
但**它意味着「降级顺序」在 0.4 档下没有可调空间**——要改只能改 ①②（已被裁决）或 ④ 的取舍顺序（= 甲/乙/丙）。

### C. 削减必要动作时「砍谁」？

**本稿不裁决（用户口径，`OPEN-ITEMS.md` 甲/乙/丙）。** 但要说明**我的候选算法是否依赖它**：

| 候选 | 是否依赖「砍谁」 | 说明 |
|---|---|---|
| **A 闭式解** | **不依赖** | 只改吸收子问题的**求解器**，`take`/`dyn[]` 语义不变 ⇒ 槽间分配仍由 (P2) 容量比例唯一确定，**不引入新的取舍自由度**。 |
| **B 上限解耦** | **不依赖**（但改基准） | 一轮到位，仍按容量比例摊。 |
| **C 对称吸收** | **依赖（间接，且波及面大）** | 它把操作槽纳入容量 ⇒ 主队 `1431`（净 143.88，占全队 65%）一旦可被吸收，**「主C 被砍」的量会大幅转移**（实测 cut 12.56 → 0，伤害 +20.4%）。这**实质上是「主C 不砍」的一种实现路径** ⇒ 与 (乙) 是同一族，**必须由用户裁决**，agent 不得自选。**⚠ 全库实测它波及 18/97 队、`max|Δdmg| +40.67%`**（§3.3）⇒ 它不是「只修主队」的局部改动。 |

**三个分支的后果（各一段）：**
- **(甲) 账本份额等比砍（现状）**：主队三槽 `账本/想打` 已实测 = 0.9350 / 0.9398 / 0.9397（`4c017472` 读数）
  ⇒ **无人被系统性亏待**，但主C 的绝对值被砍最多（因为它的账本最大）。**候选 A 在这个分支下零影响。**

  （`s = 0.94159 < 1`）⇒ **要求他们多背，只能靠提高 r 或放大 `d_i` 的上界**——即 (乙) **在 0.4 档下不可行**，
  必须与候选 B/C 或改 r 联合。**这是「依赖关系」的硬结论**：**(乙) 不是一个可以单独选的选项。**
- **(丙) 先砍超账本部分**：现状 §1.5 已显示有一支队（`yidhari-norma-lucia`）的截断**正是因为行 > 本槽账本**

## §6 否决记录（本稿排除的方案 + 为什么 + 带数字）

> 格式按 AGENTS 规则 16③（试过又放弃的方案必须留痕）。

1. **「提高吸收上限到 0.6+ 来消截断」——不再重提。**
   数字上有效（主队 `cut 12.56 → 0`，伤害 `111.32 → 117.96M`），
   但用户 2026-10-05 已裁决维持 0.4（「初始默认 40% 就按 40 来算」）。**本稿只把它列为可观测的后果，作为建议。**

2. **「把 8 轮上限调小以省算力」——❌ 实测有害，禁止。**
   上限 1 轮 ⇒ `take 29.6813 → 30.7860`（**偏大 1.105s**）、`cut 12.557 → 11.024`
   —— 看似「截断更少」，实为**吸收量虚高**（容量被违反）。非单调（§1.6③）。

3. **「标准 water-filling / max-min 公平直接套用」——❌ 推导否决。**
   (P1) 的上界含 `d_i` 自己且 `s` 全队耦合 ⇒ 无「固定上界」结构 ⇒ 填满即钉住的范式不成立。
   本问题全局只有 1 个自由度（§3.5）。**引用它属于名字联想。**

4. **「线性规划（LP）」——❌ 推导否决。**
   槽间分配由容量比例 (P2) **唯一确定**，**没有可优化的决策自由度** ⇒ LP 在这一层退化。
   真正有自由度的是「谁是操作角色」（现状 = 净必要最大）与「谁可被吸收」（候选 C），
   那是**组合/建模**问题，不是 LP。

5. **「`yidhari-norma-lucia` 那 0.95s 截断也归因到吸收上限」——❌ 实测否决。**
   它 `Σ净 = 147.80 < 180`，**闸门未开**、`Σdyn = 0`；r 扫 0→1 六档读数**恒 0.950**。
   它的机制是**行 > 本槽账本**（`assembleSlot` 整数装包）。**两者必须分开归因。**

6. **「候选 C（对称吸收）可直接采纳因为它把 cut 清零」——❌ 实测否决（本稿最重要的否决）。**
   ① 它改的是**物理模型**（操作角色能否被并行），不是算法；
   ② **波及面远超所需**：全库 **18/97 队**被动到、`max|Δdmg| = +40.67%`（`banyue-qingyi-lucia`），
      而它想解决的截断只有 1 队 12.56s ⇒ **收益/代价严重错配**；
   ③ 实测 `Σ净 220.85 → 270.48`（吸收量反馈进需求）⇒ **正反馈结构**；
   ④ 它与裁决项 (乙) 是同一族 ⇒ **属用户口径**，agent 不得自选。

7. **「用 `recommendedBuild:false` 的口径读数做容量账」——❌ 实测否决（方法陷阱）。**
   同一队 `cut` 12.56s vs 0.95s，会把归因指向完全错误的队。**必须用 `timeGolden` 口径。**

8. **「在同一 harness 内连续切变体做全库 delta」——❌ 实测否决（方法陷阱）。**
   热启动种子被前一变体污染（读数自相矛盾：`Σ容量=38.85` 却 `take=90.475`）。
   **变体对比必须每变体独立 harness。**
