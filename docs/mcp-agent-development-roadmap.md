# ZZZ 计算器项目长远规划：Agent 全生命周期开发体系与演进路线图

> **文档标识**：`docs/mcp-agent-development-roadmap.md`
> **制定周期**：2026 年下半年至 2027 年
> **核心定位**：确立绝区零（ZZZ）高精度伤害计算引擎的长期演进路线，重点规范业务实体角色（In-game Agent）的全生命周期开发流程，并融合 AI 研发智能体（AI Engineering Agent）的自动化协同机制。

---

## 一、 战略定位与宏观愿景

### 1.1 项目定位
本项目致力于构建业界最高精度、机制最完备、代码具备强类型保障与自验证能力的绝区零战斗数值仿真与计算引擎。核心口径立足于**整局总量物理平衡与局部爆发轴仿真**，覆盖全收录角色的资源循环、属性转模、招式倍率、影画命座、核心被动与队伍协同效果。

### 1.2 "双 Agent 融合"架构心智模型
在本项目语境下，"Agent" 具备双重关键内涵，两者深度耦合、互相驱动：
1. **业务实体 Agent（Game Agent / 角色）**：计算引擎建模的核心对象。每个角色是一组复杂的机制规则、招式集、资源池、属性状态机与数值转换的集合。
2. **研发引擎 Agent（AI Engineering Agent / 智能体）**：驱动工程持续演进的自治劳动力。基于 ShunCode / Claude / DeepSeek 架构，执行从解包挖掘、语义拆解、契约签订、代码实现到回归断言的全闭环开发。

```
+-----------------------------------------------------------------------------------+
|                              研发引擎 AI Agent (协同层)                           |
|  [调度自循环] -> [证据包固定] -> [机制契约拆解] -> [AST代码生成] -> [三阶全量回归] |
+------------------------------------------+----------------------------------------+
                                           | 持续驱动与交付
                                           v
+-----------------------------------------------------------------------------------+
|                              业务实体 Game Agent (引擎层)                         |
|  [解包事实源] -> [声明式 Spec] -> [TS 机制模块/钩子] -> [状态机/资源池] -> [多轴仿真] |
+-----------------------------------------------------------------------------------+
```

### 1.3 核心战略目标
* **准度至上**：拒绝粗暴的一视同仁近似，实现精确到招式段落、执行级消耗与真实乘区的微观物理级模拟。
* **交付高效**：游戏版本发布后 **24 小时内** 完成新角色机制全量录入与自验证；老角色重构保持 **零回归（Zero-Regression）**。
* **架构自治**：告别巨型中心化上帝接口，全面推行模块化自治架构与声明式契约。

## 二、 核心指导思想与研发红线（17 条铁律实践准则）

全生命周期开发流程严格受 `AGENTS.md` 17 条铁律与 `docs/AGENT_RECORDING_SOP.md` 约束，以下四项为最高执行红线：

1. **★ 永远选长期（Long-Term Over Shortcuts）**
   任何设计决策、代码实现必须经得起跨版本迭代检验。严禁"先凑合跑通"、"少改一点代码而造临时 hack"、"因怕数字难看而伪造覆盖率"。
2. **防死数据与消费端闭环（No Zombie Fields）**
   **Spec 不是终点，代码消费端才是。** 严禁仅在 JSON spec 填写字段却无任何引擎函数读取消费（历史教训：战栗减抗字段空转）。每个录入机制必须有对应的调用点与差分生效测试。
3. **加成归入既有乘区，禁止独立乘区（Strict Multiplier Taxonomy）**
   所有伤害与机制提升，必须明确归入引擎现有的 7 大核心乘区（基础攻击、攻击力%、增伤%、双暴、穿透、防御、抗性、失衡/异常积蓄），严格执行同区加算，杜绝私造行级独立乘区。
4. **事实源与断言强制查证（Zero Hallucination）**
   严禁凭游戏名联想推断音擎归属、招式 ID 或属性类别。跨实体断言前必须跑 `node scripts/resolve.mjs` 核验，派生数值以引擎探针（`probe:panel`）为唯一事实。

## 三、 Agent（角色）全生命周期开发流程 2.0（SOP）

将角色研发划分为六个标准化阶段，每个阶段均有机器可验证的准入与准出条件：

```
[阶段一: 证据固定] -> [阶段二: 机制契约] -> [阶段三: 模块实现]
        -> [阶段四: 招式限定与轴] -> [阶段五: 三阶验证] -> [阶段六: 漂移防御]
```

### 3.1 阶段一：证据固定与数据源接入（Evidence Anchoring）
* **目标**：锁定原始解包证据，建立角色事实基准，防止上游漂移。
* **操作规范**：
  1. 运行 `node scripts/resolve.mjs agent <id>` 确认角色唯一身份与中英日键位。
  2. 运行 `node scripts/record-agent.mjs init <id>`，从 `data/raw/nanoka_missing/full/<id>.json` 读取原始数据，生成 `data/recordings/<id>.json`。
  3. 针对倍率表招式与文本映射，严格调用 `scripts/lib/move-elements.mjs`，通过**技能描述散文 + 段序号**解析物理与元素属性，严禁按 `skill_list` 编号硬套（彻底规避历史 690 个同号错位与洛克茜风属性误判问题）。
* **准出条件**：`data/recordings/<id>.json` 生成成功，包含完整的句段指纹与 JSON pointer，拒绝覆盖式重复 init。

### 3.2 阶段二：机制语义拆解与契约制定（Semantic Contract）
* **目标**：将自然语言文本逐句解构，消除歧义，确立确定性等级与计算维度。
* **操作规范**：
  1. **逐段决策（Decisions）**：每个文本句段赋予恰好一种决策状态：
     * `modeled`：明确映射为计算机制；
     * `out_of_scope`：排除出计算（明确记录理由及对期望收益的偏差评估）；
     * `blocked`：存在官方文本缺失或引擎通道不足，集中生成人机问答单向用户求证。
  2. **确定性四级分类（Certainty Taxonomy）**：
     * **L0（Catalog 直读）**：面板、等级成长系数、基础倍率，由导入脚本自动覆盖。
     * **L1（Deterministic Rule）**：确定规则（如"每 12 秒触发一次"、"精通按 0.15 转攻击"），AI 确定性实现。
     * **L2（Approximation with Sliders）**：实战波动机制（如"受到攻击后获得"、"覆盖率 60%~90%"），**必须显式暴露滑块**，由用户配置覆盖率/占比。
     * **L3（User-Meta Decisions）**：排轴极限操作（如极限闪避接连携、合唱排刀），由用户拍板基准方案。
  3. **契约落地**：对照 `docs/MECHANIC_PATTERNS.md` 选定 D1~D9 计算维度，在 recording 文件中预写输入与期望值的测试用例。
* **准出条件**：`node scripts/record-agent.mjs check <id> plan` 返回 exit 0。

### 3.3 阶段三：声明式 Spec 与 TypeScript 机制模块实现（Implementation）
* **目标**：代码落盘，遵循单一职责与高内聚设计。
* **操作规范**：
  1. **声明式 Spec（`src/specs/agents/<id>.json`）**：
     * 录入 `attributeConversions`（属性转模）、`resources`（专属资源池）、`events`（事件钩子）、`verifications`（基准数值）。
     * 遵循 `src/specs/template.json` 规范，标注 `[已确认]` 或 `[猜测·高/中/低]`。
  2. **TS 机制模块（`src/mechanics/agents/<name>.ts`）**：
     * 仅当声明式 spec 无法表达复杂动态逻辑时介入（如动态时间折叠、连携状态拦截）。
     * 实现 `AgentMechanicModule` 规范钩子：`buildCharConfig`、`patchExecutions`、`beforeDamage`、`afterDamage`。
     * 必须在 `src/mechanics/index.ts` 注册，严禁孤儿模块。
* **准出条件**：编译通过，无类型报错，代码符合 ESLint / Prettier 规范。

### 3.4 阶段四：精确招式限定与多轴仿真（Scoping & Stun Integration）
* **目标**：杜绝全局粗暴加成，落实招式微观物理命中与失衡轴收益。
* **操作规范**：
  1. **招式限定（Move-Specific Scoping）**：文本明确指出"某招提升"时，必须限定至对应 `moveId`，禁止扩大至全招式或面板级生效。确需等效近似时，按 `边际增益 × 该招占总积蓄/伤害比例` 进行加权，并在注释中详录公式。
  2. **执行级消耗与分段（Execution-Level Consumption）**：强化特殊技、终结技分段命中必须挂载到具体执行行；消耗层数按实际施放扣减（参考安比 6 命执行级按次消耗设计）。
  3. **失衡轴与时间预算联动**：接入 `stunAxis` 与 `useResourceCalc`，确保角色前台时间精确计入 `necessaryTime`，平 A 池按溢出时间比例正确压缩。
* **准出条件**：角色在 0 命与 6 命状态下均能正确参与单轴与全队资源迭代循环。

### 3.5 阶段五：三阶金字塔验证网（Three-Tier Verification）
* **目标**：构筑铜墙铁壁般的质量防线，保证任意重构零破坏。
* **层级架构**：
  * **Tier 1: 契约自检（Contract Linter）**
    `node scripts/record-agent.mjs check <id> complete`
    验证字段、调用点、断言函数真实存在且命名对齐。
  * **Tier 2: 差异化生效单测（Differential Unit Tests）**
    基于 `src/test/harness.ts` 搭建公共 harness；针对每个机制编写**正例、反例、边界例**测试，重点测试滑块扰动（例：滑块调 0/0.5/1 时，数值必须产生对应阶梯差异）。
  * **Tier 3: 全局不变量与构建全体验收（Full Sweep & Verify）**
    `npm run verify`（串联 check-guards, check-tokens, validate:data, validate:specs, vitest, build）。
    包含 `allAgentsSweep.test.ts` 全角色 × 0/6 命座单射遍历，确保历史角色零抖动。
* **准出条件**：`npm run verify` 一次性绿灯，CI 校验全通。

### 3.6 阶段六：漂移防御与生命周期闭环（Drift Defense）
* **目标**：建立长期演进的防腐机制。
* **操作规范**：
  1. **版本对齐**：上游数据源（如 Nanoka / 游戏客户端热更）变动时，执行 `packet <id>` 自动化 diff，高亮提示变化段落。
  2. **历史燃尽**：严格按计划消解 `data/recordings/legacy.json` 中的存量未复核角色，每重构一员即从豁免清单中划除。
  3. **状态自动同步**：执行 `npm run docs:status`，自动刷新 `docs/implementation-status.md`。

## 四、 关键系统演进战役（Strategic Technical Milestones）

为支撑未来 100+ 角色与更复杂的战斗体系，系统架构需完成以下四大战略重构：

### 战役 1：角色配置去中心化（De-monolithic Config Container）
* **现状痛点**：`CharacterOperationConfig` 膨胀为包含数百个不同角色专有字段的巨型 interface，类型污染严重，跨角色拼写错误无法在编译期暴露（对应 `.claude/OPEN-ITEMS.md` D2 事项）。
* **重构方案**：
  1. 建立基于泛型/命名空间的角色专有配置容器：`AgentSpecificConfig<T>`。
  2. 角色专有字段从主配置接口迁出，由各角色机制模块自主声明并由 TS 强类型保障。
  3. 推进路线：
     * **阶段 A**：通过 AST 自动化分析脚本产出全量"字段 -> 写入模块 -> 消费引擎"拓扑矩阵；
     * **阶段 B**：在 `resource.ts` 引入基于 Map / Record 的类型安全隔离访问层；
     * **阶段 C**：逐批迁移 43+ 角色，彻底拆除巨型接口。

### 战役 2：L0/L1 机制代码的 AST 自动生成器（Codegen Engine）
* **现状痛点**：约 46% 的机制属于结构简单的确定性规则（L1），反复手写模板代码消耗大量精力且容易引入拼写失误。
* **重构方案**：
  1. 依托 `docs/MECHANIC_PATTERNS.md` 积累的 D1~D9 模式词典，开发代码合成器 `scripts/codegen-mechanic.mjs`。
  2. 输入结构化契约 JSON，自动生成标准规范的 `spec.json` 节点、TS 钩子函数体及标准 Harness 测试用例。
  3. 人工与 AI 的精力全面聚焦于 10% 的高价值 L3 轴设计与复杂异常交互。

### 战役 3：统一招式分类学与微观元素事实源（Universal Move Taxonomy）
* **现状痛点**：多段攻击中物理与属性伤害交替出现（如安比普攻 1~3 段物理、第 4 段及落雷电伤），目前依赖散文正则提取，缺乏全引擎公用的统一结构化事实源。
* **重构方案**：
  1. 在 `public/static/catalog.json` 中将 `SkillMove.rows` 升级为具备命中时间戳、分段元素、独立削韧值、能量回复标签的完整向量。
  2. 伤害计算层全面支持 Sub-Move 行级结算，消除任何层面的元素判定歧义。

### 战役 4：从静态总量折叠向轻量事件流状态机演进（Timeline & State Machine）
* **现状痛点**：当前计算模型核心为"整局总量收敛"，面对多状态重叠、动态快照机制（Snapshot vs Real-time buff）、窗口期严格依赖（如连携后 5 秒内）存在估算边界。
* **重构方案**：
  1. 保持外层快速计算性能优势的同时，引入微观时间片状态机（`src/specs/stateMachine.ts`）。
  2. 针对失衡窗口与异常紊乱爆发段，支持高精度的微时间轴仿真，实现"双轨制计算"（宏观总量概算 + 微观爆发精确帧仿真）。

## 五、 AI Agent 研发工程化保障体系

为保障 8~10 小时以上无人值守的自动化平稳开发，确立以下工程底座：

### 5.1 管理员链条自循环协议（Self-Sustaining Admin Loop）
* **机制设计**：每一任管理员 Agent 会话结束前，必须自动完成：
  1. 当前轮次成果验收与 `git status` 状态确认；
  2. 检查 `docs/AGENT_ID_BURNDOWN_LOG.md` 燃尽进度；
  3. 在交接文档（`PROMPT-handoff-roundNN.md`）输出**下一任管理员启动指令**并触发派发，杜绝任务链中断。

### 5.2 协作拓扑与并发规约
* **1 + 3 拓扑模型**：1 个主控管理员会话负责任务编排、契约审查与合并验收；最多 3 个工作者（Worker）会话并行推进独立角色的单测与实现。
* **文件锁与 Git 护栏**：
  * 严禁执行 `git add -A` 或 `git commit -a`，必须显式提交具体改动文件路径；
  * 受保护目录（`.claude/ledgers/`, `.zc/`）严禁入库；
  * 全文本强制 LF 换行，避免 CRLF 引起的跨平台文件 churn。

### 5.3 债务闭环登记（Debt Registry）
* 探索性开发中发现的技术债务（如暂未建模的次要分支、近似估算），严禁以无主注释留存。
* 必须在源码标注 `debt: <天花板>, <升级路径>`，并在 `scripts/check-guards.mjs` 的 `DEBT_REGISTRY` 正式登记，还清后严格注销。
