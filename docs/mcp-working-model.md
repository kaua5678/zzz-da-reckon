## 0. 一句话结论

**分工改成「单一执行者 + 按需外包机械活」；规则只保留「防真实事故 / 防边界倒退」的，计数棘轮降级为「只防增加」；工作方式从「逐卡推进」改为「先画地图，再按清单集中做」。**

## 1. 问题一：分工该不该有、怎么分

**现状（实证）**：
- 第 102–119 轮的全部卡（arch 卡表 CC-83…CC-98、R1–R4、R7）都由 lead 直接完成，这 18 轮没有派出过子代理。
- 队列文档 427 行，大部分是 lead 写给下一个自己的交接，不是写给 worker 的任务卡。
- 「lead 写待办，worker 执行」在实际运行中已经名存实亡，却还要维护：交接格式、认领纪律、队列置顶。

**决定**：
- **废除固定的 lead / worker 分工**。每个会话都是完整的执行者：自己读全貌、自己判断、自己做完。
- 子代理（dsh）**只外包「输入输出都能写死」的机械活**，例如批量统计、生成夹具、按清单机械替换。派出前必须能写出验收命令；不外包需要判断的事。
- **不再为「低级模型」预写待办**。需要判断力的事写成「问题 + 已知事实 + 我的倾向」，由下一个会话判断，而不是写成照做步骤。

**为什么**：用户说「也许分工才是牢笼」，这个判断和实证一致。分工的维护成本真实存在，收益为零。
更大的问题在于：「写给别人执行」迫使任务被切成局部卡，这正是 R6 批评的「局部信息 → 局部改」的来源。

**回退**：若以后确实有并行的多个执行者，再恢复队列认领纪律（旧规则在 git 历史里）。

## 3. 问题三：工作方式

**现状**：「读队列 → 接卡 → 局部改 → 提交」。每轮只读局部，所以只能做局部卡。已经做了 98 张 CC 卡，用户仍然说「逻辑没达到正确」「不知道 opus 有没有掌握全貌」。

**决定：改为三段式，按阶段推进，不按卡推进**：
1. **画地图（R6 第 1 步）**：写 `docs/ARCHITECTURE-OVERVIEW.md`，记录实际分层、数据流和每层职责，是读代码得出的现状，不是转述规划文档。
2. **对账（R5）+ 找机会（R6 第 2 步）**：在地图上标出「规格没实现对的地方」和「冗余 / 分裂 / 特判」。两者共用同一次读码，结论会互相印证（R5 的零读取往往就是 R6 的冗余或分裂）。
3. **集中重构**：按清单挑影响面最大的一块，连续几轮做透，而不是每轮换一张卡。

**R 编号顺序调整（R8 授权，写明理由）**：
- 用户给的顺序是 R5 → R6。我改为 **R8 执行项 W1–W4 → R6 第 1 步（地图）→ R5 第 2 刀 → R6 第 2 步**。（第 121 轮：W 系列已经收尾，下一步是 R6 第 1 步。）
- 理由：
  - R5 第 2 刀要核实的 Z4、Z6、Z2、K0，都需要读 `core/buff.ts`、`inCombatBuffs.ts`、`panel.ts` 的效果管线。这正是地图要画的部分，先画地图能避免读两遍。
  - W1–W4 是减负，做完再干活，每轮的维护成本立刻下降。
- R5 不降级。它是地图之后的第一个技术任务。
- **回退**：若下个会话判断地图工作量过大、拖慢 R5，可以只画「效果管线」一段就转去做 R5，并把判断写在这里。
